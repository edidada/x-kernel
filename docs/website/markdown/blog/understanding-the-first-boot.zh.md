第一次运行一个操作系统项目，最容易把注意力放在最后那个 shell 提示符上。它意味着系统终于可以接受输入，但在它出现之前，配置、构建工具、内核、设备和用户态已经完成了一连串交接。

把这些角色分开看，启动就不再只是“执行 make run，然后等”。

## 配置决定要构建的系统

同一份 X-kernel 源码可以面向不同架构和平台。开始构建前，要先回答：这次运行在哪个平台上，启用哪些能力？

AArch64 QEMU 示例从平台配置开始：

```bash
cp platforms/kplat-aarch64/qemu_defconfig .config
make defconfig
```

第一条命令选中平台提供的最小配置，第二条将它展开为完整配置。这里的 `.config` 是后续构建的重要输入，而不是可有可无的记录文件。复制前应保存需要保留的自定义配置。

## 内核和 rootfs 不是同一个东西

内核负责管理资源、响应系统调用和协调设备。根文件系统提供用户态程序和文件。内核成功输出启动信息，并不说明镜像里的 shell 一定可用；反过来，准备好 rootfs 也不等于已经构建了内核。

![配置、内核与根文件系统在 QEMU 中汇合](../assets/blog/first-boot-zh-CN.svg)

当前入门流程分别准备它们：

```bash
make rootfs
make build
make run
```

`make rootfs` 获取预构建的文件系统镜像，`make build` 根据配置生成内核产物，`make run` 使用相应平台设置启动 QEMU。完整依赖安装与操作步骤见[快速开始](/docs/zh-CN/quick-start)。

## QEMU 提供一台可重复启动的机器

QEMU 在这里承担机器环境的角色。CPU 架构、内存、设备和串口等设置影响内核面对的运行条件。内核仍要完成它自己的初始化，并使用相应驱动与设备交互。

这种分工也解释了为什么“支持 AArch64”不能直接理解成“支持所有 ARM 板卡”。平台与设备的组合仍然重要。

## 日志是一条时间线

读日志时，先找阶段，再找错误。构建阶段是否已经完成？QEMU 是否成功启动？内核是否有串口输出？问题发生在初始化过程中，还是进入用户空间之后？

这些问题比最后一行错误更能缩小范围。比如，找不到 QEMU 可执行文件属于主机环境问题，不需要先修改内核；镜像下载失败则应先看网络、文件路径和磁盘空间。

当使用提供 shell 的 rootfs 时，`pwd` 和 `ls /` 可以帮助确认用户态确实在运行。提示符的用户名与主机名属于镜像环境，不是判断内核版本的可靠依据。

## 第一次成功之后，先保留基线

记录仓库提交、使用的 defconfig、工具链版本和镜像来源。接下来每次只改一项配置或一处行为，再比较结果。

这样，当后续出现问题时，你可以回答“与上一次成功相比改了什么”，而不需要重新猜测整个环境。

启动是一个值得记录的里程碑，也是阅读系统的入口。更有价值的下一步，是沿着日志找到对应代码，理解某一个阶段如何把控制权交给下一阶段。

*本文解释仓库当前启动流程，不声明本轮进行了新的完整内核构建或性能测试。遇到问题可按[获取帮助](/docs/zh-CN/getting-help)收集复现信息。*

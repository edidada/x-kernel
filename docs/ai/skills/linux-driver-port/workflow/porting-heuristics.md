# 移植直觉：跨驱动复用的判断准则

这份文档不写某个外设的位段，也不写某个子系统的 API。它写的是**移植过程中反复出现的判断错误**，
以及能提前拦住它们的机械动作。每条都附一条来自实际移植的证词（多为 USB 主机栈，但结论与外设无关）。

配套阅读：`workflow/port-workflow.md`（阶段流程）、`references`/`data/`（位段与 API 真相）、
`examples/rk3588-pcie/bring-up-log.md`（本板实测记录）。

---

## 0. 一句话总纲

**移植的失败几乎不来自"抄错了值"，而来自"少了一个动作"或"多了一个想当然的等价变形"。**

所以移植工作的重心不是抄位段，而是：

1. 把参考里**每个动作**列全（缺席的检查，见 §1）；
2. 把每个有生命周期的结构**当整体**看懂（不可局部等价，见 §2）；
3. 把"状态归谁持有"分清（见 §3）；
4. 让每次失败都能**排除一个假设**（见 §7）。

---

## 1. 缺席是看不见的：先做"动作清单"，再写代码

**错误模式**：逐字段抄对寄存器定义，却漏掉参考里某个 *调用*。值是抄对了，动作没做。
这类 bug 没有编译期特征，也没有可对照的"错值"，只能靠清单发现。

**做法**：动手前，把参考驱动在 **probe / open / enqueue / 完成 / 出错 / teardown** 六个环节里的
所有"外部动作"列成表，逐行标注 `已移植 / 不适用(理由) / 缺失(进缺口报告)`：

- 对设备的**协议请求**（类请求、厂商请求、标准请求）；
- 对**框架/子系统的注册与告知**（注册、使能、上报、通知、claim）；
- 对**硬件其它块**的动作（时钟、复位、PHY、电源域、IRQ 使能、IOMMU 配置）；
- 对**共享资源**的动作（其它控制器也在用的引脚/电源/校准值）。

USB 的证词：链路 `enabled`、端口 `U0`、slot context 逐字段与参考一致，但下游设备永远
`Address Device` 传输错误——缺的是参考对一个非 root SuperSpeed hub 必发的类请求
（`HUB_SET_DEPTH`）。寄存器定义里永远找不到它。

> 机械检查：新接一个设备类时，先在参考里 grep 该类所有 control 请求常量，再逐个确认"我们发了没有"。
> 对"缺席"这类 bug，**只有枚举法有效**。

## 2. 有生命周期的结构，禁止"局部等价变形"

**错误模式**：参考把某个结构做成"硬件停靠在一个固定地址上、软件把内容换上去"，我们改成
"软件每次改写指针"。纸面上两者语义相同，硬件上不是：有些字段只有硬件在改（序列号、翻转位、
当前指针），软件去写就把它弄丢或与硬件打架。

**判定：这个结构属于哪一类？**

| 类别 | 例子 | 移植方式 |
| --- | --- | --- |
| 纯配置（写完就不动） | 波特率、位宽、滤波表 | 按字段抄，可自由重构 |
| 队列/环（生产者-消费者） | 描述符环、DMA ring、fifo | **整段 diff**：构建、入队、判完成、拆解四个函数一起看 |
| 有所有权的链表 | 异步表、就绪队列、hash bucket | 先写下**所有权与空态规则**，再对照 |
| 硬件维护状态的块 | 传输上下文、通道、端点 | 见 §3 |

**做法**：把参考的四个动作函数 `sed` 出来（构建 / 入队 / 判完成 / teardown），逐字段、逐步骤
diff，并在 commit message 里写明读了哪个函数。字段级 diff 通过**不能**作为"机制已对齐"的证据。

USB 的证词：位段全对，机制全错——异步表的空态参考是"头指向自己"，端点每次插入再摘出；
我们建了静态环，"摘出"于是读作自指。四种不同面孔的症状由此而来。

## 3. 状态归谁持有：三方对照表

**错误模式**：把"硬件替你维护的状态"当常量重写，或把"设备维护的状态"当无状态协议。

对每个会跨操作存续的变量，填写归属：

| 变量 | 软件持有 | 控制器持有 | 设备持有 | 谁在何时更新 |
| --- | --- | --- | --- | --- |
| 数据翻转位 | ? | 是（上下文里） | 是（端点内） | 每包 |
| 序列号 / tag | 是 | – | 是（回显） | 每命令 |
| 通道/槽位分配 | 是 | 是（上下文） | – | 每次建立 |
| 重试计数 | 是 | 是（CERR 等） | – | 每次错误 |

**规则**：

- 硬件/设备持有 → **继承**（从上下文/回包读回），不能重置为常量；
- 三方都在维护同一语义时 → 找出**协议规定的相位边界**，在那里显式同步（这是唯一合法的重置点）；
- 软件持有 → 必须随对象生命周期显式初始化与清理。

USB 的证词：bulk 一直发"翻转位=0"，几十笔之后设备因不匹配丢弃所有包；
控制器把这个位存在上下文 overlay 里，唯一正确做法是从那里继承。

## 4. 每个 reset/复位原语先问"爆炸半径"

**错误模式**：在恢复路径里随手用一个很强的复位，把还在正常工作的东西一起毁掉，
然后拿"恢复后还是不行"当成另一个 bug 去查。

**做法**：给用到的每个复位原语列一张表，写清"它摧毁什么、谁的职责是重建它"：

| 原语 | 摧毁 | 参考里谁负责重建 |
| --- | --- | --- |
| 控制器 reset | 端口状态、调度表、寄存器配置 | 上层重新枚举（USB 核心的 hub 线程） |
| 端口/通道 reset | 对端状态、地址/序列号 | 本驱动重新 address/配置 |
| 端点 halt 清除 | 端点 halt + 翻转位 | 只需重发该笔 |
| 设备整体 reset | 全部软件状态 | 驱动重新 probe 流程 |

**判据**：如果参考敢用强复位，一定存在**某个东西**替它收拾残局（上层重枚举、框架重新 probe、
用户态重连）。我们若没有那个东西，强复位就不是"可用的恢复手段"。

USB 的证词：HSE 恢复里用了控制器 reset，结果把已挂载设备也弄掉了——参考敢这么做是因为
它之后会有整树重枚举，而当时我们没有这条路径。

---

## 5. 重试与延时不是机制；参考的每次等待都有理由

**错误模式**：现象偶发 → 加 retry；时序不对 → 加 sleep。真实机制缺口被"有时能过"掩埋，
并且付出持续代价（启动时间、寄存器扰动、更长的 triage）。

**规则**：

- 加 retry 前先回答："如果它需要重试才能过，缺的机制在哪？"
- 参考里的重试/延时是**有注释的硬件怪癖**（"有些设备需要额外的 X ms"、"这个控制器必须…"），
  移植时连注释一起搬；自己发明的兜底不算移植；
- 把 retry 的成本量化：每轮上板记录启动时间/失败代价。**启动时间回退是"你在补偿而不是在移植"的信号**。

USB 的证词：5 次端口 reset、失败端口 disable、10 ms settle、warm reset 阶梯、HSE 重试——
一条都没修好根因，启动时间从 75 s 涨到 129 s，并且让我更晚看真因。

## 6. 热插拔与"回来"是移植范围的一部分

**错误模式**：把"枚举一次成功"当验收标准。设备掉线又回来之后，驱动发往一个没人应答的地址，
于是看起来像"传输偶发失败"。

**做法**：凡是可移除的实体（设备、卡、链路、对端），移植必须包含：

1. 检测（状态位的变化，而不是传闻）；
2. 重建（用**原有身份/地址**重建，让上层持有的对象继续有效）；
3. 幂等（同一路径重复执行不积累状态）。

USB 的证词：最终打通读写的唯一修复就是"掉线后按原地址重新建立"——而它此前被当作"额外的鲁棒性"，
实际是功能的一部分。

## 7. 诊断的原则：一个实验必须能排除一个假设

**错误模式**：日志越加越多，每条都很"详细"，但没有一条能区分"是 A 错还是 B 错"。
（这轮我把整环 dump 了三次，三次内容完全相同，反而加深了误判。）

**做法**：

1. **先写下两个假设**，再设计输出；输出不能区分二者就别加；
2. 观察点放在**状态变化**上（变化时才打印），而不是每个事件；
3. 打印**硬件实际看到的东西**（读回的结构、上下文、握手状态），不是你打算写的东西；
4. 分层定位：把探测放在**能回答该问题的那一层**（例：判断"是不是共享控制路径坏了"，
   只能在"设备还有可用管道"的那一层做长度变体实验）；
5. 一次只改一个变量；两轮不同现象要能落到"同一根因"或"确实不同"的判据上。

**复用性最高的三个实验形态**：

- **变体扫描**（同一条命令用不同长度/参数各试一次）→ 分离"命令内容"与"公共路径"；
- **结构快照**（把驱动写的上下文/描述符读回来打印）→ 分离"意图"与"实际"；
- **变化日志**（只在状态位变化时打印 + 时间戳）→ 分离"传输打死它"与"它自己死了"。

## 8. 数据通路正确性与语义正确性必须分开验证

**错误模式**：把"解析失败"直接归因为驱动 bug（或反过来，把"能读"当成"读对了"）。

**做法**：先构造一个**只依赖数据通路**的判据（签名、校验和、已知常量、回读比对），证明
"字节是对的"；再用它判断"内容是什么"。写路径同理：写一段可校验的内容，再读回比对。

USB 的证词：`boot sector 逐字节正确（EB 63 90 … 55 AA）`证明 bulk 通路正确，
"读不到 ext4 超级块"其实是介质不是 ext4；另有一次按产品名字猜设备类型，猜错两次。

## 9. 参考的权威性是分层的

**错误模式**：拿一个上游版本当唯一真相，然后在"平台胶水"上反复失败。

**做法**：明确分层的权威源，并在缺口报告里标注来源：

| 层 | 权威 |
| --- | --- |
| 设备类/协议语义 | 规范 + 上游主线 |
| **平台胶水**（时钟/复位/PHY/电源域/引脚/私有寄存器） | **板子自己的 BSP 源码** |
| 本项目的框架契约 | 本仓的边界文档与 skill |

**判据**：同一段逻辑，如果上游与 BSP 不一致，先问"这段是通用还是胶水"再决定听谁的。
并且：**胶水的数值必须实测**（PHY/寄存器/时钟），源码只给"写什么"。

---

## 10. 用"第二实现"和"活体"做二分

**错误模式**：在没有对照的情况下反复推理。

**做法**：手上有三个可用对照，优先级如下：

1. **参考板上的活体**（能跑的同一硬件）——最强，但注意不要为了观测把它弄坏；
2. **另一个实现**（同项目的另一套栈、另一棵树的同一驱动）——用来确认"协议层是否一致"，
   差异会集中在初始化与胶水；
3. **U-Boot / 固件的行为**——免费的寄存器 oracle。

**判据**：如果两个实现的控制序列逐字段相同，问题几乎必然在"初始化顺序/胶水/共享资源"，
而不是协议本身。

---

## 11. 何时停止打补丁，改为整段重读

**触发条件（满足任一即停手）**：

- 连续两次"点状补丁"没有改变失败形态；
- 修复点是"为了让 A 过而让 B 也成立"，而不是"恢复了参考本来就有的机制"；
- 开始需要引入参考里没有的重试/延时/特判才能前进。

**动作**：回到 §2，把该路径的四个动作函数整段 `sed` 出来重读；并把"我们与参考的结构差异"
写成一句话（所有权/空态/字段归属哪里不同），而不是继续调参。

---

## 12. 记录负面结果与判据，而不只记录修复

**错误模式**：只写"修了什么"，于是下一个人重复排除同样的假设。

**做法**：bring-up 日志 / commit message 里保留：

- 被**证伪**的假设（以及用来证伪的那条证据）；
- 用来判断"好/坏"的**具体行**（哪个日志、哪个寄存器值）；
- 每轮的**成本**（启动时间、失败代价），让"补偿性修改"有账可查。

---

## 13. 验证纪律（与具体外设无关，但决定 triage 速度）

- 配置决定编译面：**板级配置与测试配置交替时**，先确认当前 `.config`，否则会出现"改了没生效/编不到"；
- 部署的是**哪一份镜像**要能说清（预构建产物 vs 本次编译）；
- 每轮上板有**时间预算**，超出就换实验设计，不要靠"再跑一次看看"；
- 一次改动**一件事**，并记录与上一轮的差异（症状是否改变形态）。

# 错误处理规则

## 规则格式

每条规则使用以下字段：

- **规则 ID**：稳定编号，review 评论和后续统计可引用。
- **规则**：应遵守的编码要求。
- **等级**：`MUST`、`SHOULD` 或 `MAY`。
- **适用对象**：需要检查该规则的代码对象。
- **判定方法**：如何判断代码是否符合规则。
- **例外**：不按本规则报告问题的情况。
- **反例**：违反规则的典型代码。
- **正例**：符合规则的典型代码，或推荐修改方式。

## CG-ERR-001：可恢复运行时失败不应触发 panic

- **规则**：非测试代码中，可能由合法运行时状态触发的失败应返回错误或显式处理，
  不应使用 `panic!`、`unwrap()`、`expect()`、`todo!()`、`unimplemented!()`
  或会 panic 的断言把失败升级为 kernel panic。
- **等级**：MUST
- **适用对象**：非测试代码中的 panic 路径、unwrap-like 调用、断言和未实现占位。
- **判定方法**：
  1. 找到新增或修改的 panic 路径。
  2. 判断触发条件是否可能来自用户输入、设备输入、固件/启动数据、配置、
     资源耗尽、并发时序、外部 crate 返回值或其他可恢复运行时状态。
  3. 如果触发条件属于合法运行时状态，且当前层能够返回错误或执行恢复处理，
     则违反本规则。
- **例外**：
  - 测试代码。
  - 已由局部检查证明不可能发生的内部不变量破坏。
  - 启动期或初始化期的 fail-stop 检查，且模块契约明确该失败不可恢复。
- **反例**：

```rust
let inode = lookup_inode(path).unwrap();
```

`lookup_inode()` 失败可能来自用户提供的路径或文件系统状态，不应触发 panic。

- **正例**：

```rust
let inode = lookup_inode(path)?;
```

## CG-ERR-002：忽略 Result 必须说明原因并保持状态正确

- **规则**：调用返回 `Result` 的函数时，不应静默丢弃错误。
  如果有意忽略错误，代码或注释必须说明原因，并保证失败后系统状态仍然正确。
- **等级**：MUST
- **适用对象**：`let _ = fallible_call()`、`.ok()`、`drop(result)`、
  `if let Err(_) = ... {}` 空处理、只记录日志但继续执行的错误路径。
- **判定方法**：
  1. 找到新增或修改的 `Result` 丢弃或降级处理。
  2. 检查是否说明了忽略错误的原因。
  3. 检查失败后是否仍保持资源生命周期、状态机、注册表、引用计数或外部可见状态正确。
  4. 缺少原因说明，或失败后状态无法证明正确时，违反本规则。
- **例外**：
  - best-effort 清理、统计、trace、日志上报等允许失败且不影响语义的路径。
  - drop 或 teardown 路径中已经没有可恢复调用方，但仍应避免破坏状态一致性。
- **反例**：

```rust
let _ = registry.insert(id, entry);
state.mark_registered(id);
```

如果 `insert()` 失败，后续状态仍被标记为已注册。

- **正例**：

```rust
registry.insert(id, entry)?;
state.mark_registered(id);
```

## CG-ERR-003：错误映射应使用统一映射并保留上层需要区分的语义

- **规则**：跨层传播或映射错误时，应优先使用该子系统已有的统一错误映射。
  映射结果应保留上层契约、调用方处理逻辑或用户可见行为需要区分的失败原因。
- **等级**：SHOULD
- **适用对象**：`map_err`、`From` / `TryFrom` 错误转换、syscall errno 映射、
  跨 crate error 转换和 fallback 错误处理。
- **判定方法**：
  1. 找到新增或修改的错误映射。
  2. 搜索当前子系统是否已有统一映射函数、`From` 实现或 error adapter。
  3. 判断被合并的错误原因在上层契约、调用方分支、用户可见 errno、
     日志诊断或恢复策略中是否需要区分。
  4. 如果代码绕过已有统一映射，或把需要区分的错误压缩成笼统错误，
     导致调用方无法执行正确处理，则违反本规则。
- **例外**：
  - 上层 API 契约明确只暴露一种错误。
  - 被合并的错误原因在当前层没有不同处理方式，也不会改变用户可见语义。
  - 当前子系统还没有统一映射，且本次局部映射完整保留了上层需要区分的语义。
- **反例**：

```rust
let file = open_path(path).map_err(|_| SysError::EINVAL)?;
```

这里绕过了 VFS 已有的错误映射，并把 `ENOENT`、`EACCES`、`EINVAL`
等用户可见语义压缩成了同一个错误。

- **正例**：

```rust
let file = open_path(path).map_err(SysError::from_vfs_error)?;
```

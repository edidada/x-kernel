## 1. 范围及确认依据

需求依据为 requirements-v0.2 的 R01—R13，以及用户后续明确确认的约束：

- 基础框架采用 Linux 模型的职责和生命周期，不只是借鉴部分算法。
- class 是 device 的功能分类；hwrng provider 注册与消费是子系统责任。
- 普通 remove 完成退出，不增加通用硬件停机失败绑定状态或重试事务。
- 成功绑定遗漏退出就销毁管理权属于 bug；probe 失败则必须有合法构造回滚。
- DeferredArc 按实际析构要求选择，不是默认依赖，不自动补做退出。
- VirtIO 显式停机及未完成请求回收作为前置需求，不能由 base 补偿。
- 已确认 HwrngRegistry、HwrngRegistration、HwrngHandle、HwrngDevice 命名，
  及 registration mod 聚合生命周期的布局。
- 已确认显式 unregister 才结束注册；凭证 Drop 不等待、不自动注销、不默认
  panic。遗漏注销留下注册及资源保活，是 bug，不是退出成功或恢复策略。

R10 的“class 发布”、验收组织中的“class 消费者”应按已确认分层理解为
“hwrng 子系统注册与消费者”，不降低真实设备接入、退出或兼容验收要求。
旧需求正文保留来源记录；不能反过来用其中旧术语强制保留泛型 Class<T>。
新增或改变外部行为仍单列需求差异，不借设计调整偷偷批准。

## 2. 责任边界与依赖方向

| 模块 | 权威事实及责任 | 明确排除 |
|---|---|---|
| 设备模型 | 设备注册、身份与关系、匹配、驱动关联及单设备管理串行化 | 家族 I/O、统一业务操作许可、猜测硬件停止 |
| 总线/枚举模块 | 描述词汇、匹配、具体实例和下游注册/注销规则 | 仅凭 parent 推断所有资源所有权 |
| 设备分类 class | 对 device 分类及既有对外呈现 | 任意 T 的服务注册/业务排空 |
| hwrng | provider 注册、发现、受控读取、使用排空和注销 | 总线匹配、设备特定 reset |
| 具体驱动 | 本次绑定 Data、请求状态、停止读者、硬件及资源收尾 | 通用退出事务和调度器实现 |
| OS 契约与 host adapter | 可移植资源语义及宿主实现 | 第二套设备身份或绑定状态 |
| entropy | 消费及来源选择、熵处理 | 取得注册权或延长硬件运行寿命 |

具体驱动依赖子系统/资源契约，host 实现契约；model 不依赖 hwrng 来完成通用
管理，hwrng 不依赖宿主调度器。引用、借用、管理权不可互换。
现有 base/class 不是目标 class：先迁移真实使用者，再决定删除旧泛型层；
不牵连旧 contracts/kclass，不为当前需求造空的 Linux class 替身。

## 3. 已收敛的生命周期

### 设备与绑定

设备注册后可以无驱动存在。匹配成功调用 probe；成功 Data 归本次绑定所有。
probe 可以先注册服务再返回；后续失败必须先回滚服务和硬件，不由核心补调 remove。
解绑调用 remove，返回后解除绑定并释放 Data，但不结束设备注册。
注销设备先结束绑定，再结束注册；最后的 DeviceRef 释放只决定对象内存寿命。
同一设备管理操作串行化；不同设备不因全局回调锁被迫串行。

parent 是拓扑关系，不是“核心自动递归卸载所有孩子”的所有权证明。
总线/控制器先停止枚举、注销其拥有的下游，再停止孩子仍需使用的父服务。
这一流程不恢复整树准备、任务局部退出计划或同任务绕过锁的通道。

### hwrng 正常解绑

1. model 保活本次绑定并调用 remove。
2. 驱动同步设置停止状态，禁止新提交，锁外唤醒读者。
3. hwrng 关闭新调用、撤下 provider、排空已进入调用，完成同步注销。
4. 驱动按 transport 契约确认硬件停止、同步 IRQ、回收请求与队列。
5. remove 返回；model 结束绑定。后续 probe 创建新 runtime 和注册实例。

第 4 步内部精确顺序由 VirtIO 前置契约证明，不将读者退出当作 DMA 停止。
旧消费者可以保留停止后的对象，但不能访问新绑定，也不能延迟必要资源解除。

### hwrng 内部机制

注册表拥有注册实例集合；唯一凭证拥有注销权；消费者只持共享引用。
关闭标记与在途计数在同一短临界区维护；provider 调用、通知、等待均在锁外。
操作许可是私有实现细节，不新增公共 ID，不以强引用数量推断业务排空。
“已关闭且在途为零”才是注销的排空条件。排空等待采用第 16 节的可靠等待
契约，不能直接接受任意 RngCompletion。构造时准备独立等待对象，不与
驱动等数据的通知源混用；复用 host 实现，不新增默认 os-api 通用同步框架。

## 7. D03 来源关联：事实、方案与验证

### 已核实的事实

- Linux struct device 的 driver 指向当前关联的 struct device_driver；驱动名字
  位于 driver 对象。really_probe 在 probe 前设置关联，device_unbind_cleanup
  在解绑清理时清空它。它不是某项历史服务永久不变的发布者身份。
- Linux struct hwrng 独立拥有 provider 的 name，hwrng_register 检查其唯一性；
  该名称用于子系统 provider 管理，不是 dev->driver->name 的别名。
- 当前 model 的 DeviceCore::driver_name 是“最后开始 probe 的驱动”的第二份
  字符串事实；BindingState 又持注册驱动对象。重绑后旧消费者经同一 DeviceCore
  查询可能得到新的驱动名，不能继续把它描述为旧 provider 的发布者。
- 当前 entropy 确实按 driver_name 包含 virtio-rng 过滤来源；测试也检查这一
  行为。不能直接删掉查询或改为接受所有 RNG，后者改变来源选择/信任范围。
- path 在设备对象已有权威来源，hwrng 生产消费者不需要额外维护一份路径副本。

### 推荐方案（整体设计候选）

区分两个查询对象，不给一个 driver_name 同时赋予两种含义：

1. 设备的当前驱动来自 model 唯一驱动关联，probe 前建立，回滚或解绑清理后
   解除。不在 DeviceCore 再缓存最后 probe 的名字；无当前关联时返回无驱动。
2. 每次 hwrng 注册的来源引用设备对象及本次提供服务的驱动注册对象。查询
   provider 的 driver_name 读取该驱动对象的名字，设备位置读取设备对象。
   只保存对象关系，不复制名称/path，不共享可变的“当前驱动”查询入口。
3. 注册关联在 probe 回调期间取得，允许服务早于 probe 成功返回而被发现；
   失败时驱动撤销该服务。来源引用不保活 DriverOps::Data，不授权硬件访问。
4. 旧 HwrngHandle 可以继续识别旧 provider，但入口永久关闭；设备重绑即使
   仍由同一个驱动处理，也创建不同 provider 实例。无需公开代际数字或全局 ID。

这里“注册对象引用”是对已有驱动定义的引用，不是新增一套可操作 BindingRef，
也不为历史查询保留整份绑定 Data。引用具体表示及模块可见性在统一接口表中
固定；设备模型不反向依赖 hwrng，不恢复 PublicationSource 的 online 门禁。

这项关联是保留当前 entropy 选择行为的适配需求，不宣称 Linux hwrng 原样
拥有相同的两个引用字段。若今后改为 provider 类型/质量策略，应另行评审行为，
不能借此次框架迁移替换。Linux provider name 的独立命名空间也不机械照搬为
通用 Publication.name；是否需要对外 RNG 名称由实际节点/属性兼容清单决定。

### 反例与验证

- 设备先绑定驱动 A、再绑定 B：当前驱动查询为 B，旧 provider 查询仍对应 A，
  旧 read 失败；不能因名字查询而恢复 A 的资源。
- 同一驱动 A 重绑：两个 provider 名字来源相同，但对象身份不同，旧句柄不复活。
- probe 注册后失败：临时服务被撤销，当前关联清空，保留句柄不获得操作权限。
- 两个设备由 A 管理：共享驱动定义不共享 provider 计数、关闭状态或运行资源。
- entropy 的 virtio-rng 过滤语义保持；不因查询到了新绑定的名字误认旧来源。

结论：D03 的问题与必要事实已查清，方案等待随完整设计验收；不能以此局部
分析进入编码。下一项查证 D04 的管理上下文与等待错误衔接。

## 8. D04 管理上下文与等待错误：不能用签名掩盖缺口

### Linux 的处理边界

drivers/base/dd.c 的 device_release_driver_internal 取得设备管理锁后进入
__device_release_driver；device_remove 调用 bus/driver remove 后继续清理。
include/linux/device.h 的设备锁是 mutex，不是跨回调禁止抢占的自旋锁。
同设备 remove 递归解绑会自等待，源码明确指出这一点；并没有准备整树退出
凭证或遇到睡眠上下文错误后恢复旧绑定的协议。

Linux hwrng_unregister 的完成等待没有资源不足错误返回。其前提是调用者
可睡眠、等待不临时申请可能失败的资源，驱动已让读者能够结束。不能仅照搬
void remove，却在下游引入合法的等待资源失败并假定调用方总能处理。

### 当前仓库事实

1. 新 model 的 DeviceServices 没有执行上下文验证接口，remove_device 也没有
   在修改状态前检查可睡眠上下文；当前检查到的直接调用主要在外置 UT。
   因此不能声称现有生产入口已经建立这条不变量。
2. 真实 HostRngCompletion 调用 CompletionWait::prepare，无等待登记分配；
   合法任务上下文中等待成功，非法上下文返回 InvalidInput。
3. 但可移植 RngCompletion 文档允许等待准备失败，现有测试包含 NoMemory。
   “这个 host 不会失败”不等于“所有符合现有 trait 的 provider 都不会失败”。
4. 管理入口的一次上下文检查不能授权回调随后持 IRQ-off/自旋锁执行注销；
   回调必须遵守锁与上下文契约，等待自身仍需验证，而不是携带永久通行证。

### 收口方向与不可采用的方案

- model 的管理边界通过最小宿主能力检查上下文，不直接依赖 ktask；不合法
  调用在生命周期状态改变前返回错误。具体接口归属随统一 host 契约定案。
- 正常退出所用 provider 必须保证：发布前完成可失败准备，合法上下文中的
  排空等待没有资源失败、超时或信号取消。这是可靠同步退出的前提，不是
  新增通用 worker、准备事务或设备失败状态机的理由。
- read 的现有可失败等待行为不能顺带删除。复用 RngCompletion 只能复用
  已核实实现，不能跳过契约差异；需明确是否收紧特定排空 provider 的承诺，
  或将可靠同步等待单独表达。尚不批准具体 trait 或新增类型。
- 驱动在 remove 内破坏调用前提属于 bug，不是硬件停机失败。不允许忽略
  unregister 的错误并继续释放资源；也不凭“前面检查过”新增未论证 expect。
- unregister(&mut self) -> KResult<()> 只能保证低层失败不消费凭证，本身
  不能闭合 void remove；前文将其当作最终解决方案的推导不成立。

D04 结论：实际 host 已有无分配等待能力，缺口在可移植契约及管理边界的
表达，不需要重构 Completion。需要补齐这一前置契约的设计，再决定注销
签名和调用方诊断；当前保留未闭合状态，不报告已经解决，不进入实现。

设计验证必须覆盖非法管理入口无副作用、合法 remove 的完整等待、回调恢复
锁/IRQ 状态、host/test provider 契约等价；不能通过只测试真实 host 的成功
路径，接受仍允许正常 NoMemory 的任意排空 provider。

## 9. D04 方案比较：复用实现，不混淆契约

补充调用方核对：生产 HostRngCompletion 只有 InvalidInput 这一准备错误；
但 hwrng、VirtIO RNG 及 entropy 的外置测试均覆盖读取/等待错误与 NoMemory。
现有读取接口的错误语义不能为简化退出而直接删除。测试 provider 也不能自动
视为适合正常 remove 排空的 provider。

| 方案 | 代价及后果 | 结论 |
|---|---|---|
| 全面收紧现有 RngCompletion，删除合法准备失败 | 改变读取等待契约并影响错误测试；本轮退出需求不要求这项行为变化 | 不推荐 |
| 接受任意 RngCompletion，遇 Err 就重试/unwrap | 重试无进展保证，unwrap 将原契约合法错误升级成 panic | 不采用 |
| 准备可转移任务等待凭证，贯穿 model/driver/subsystem | 增加任务绑定、传递和上下文管理，恢复已撤回准备事务方向 | 不采用 |
| 单独表达可靠同步等待保证，复用现有 host 等待实现 | 增加小范围契约，但不增加队列算法、worker 或退出状态机；读取行为不变 | 推荐候选 |

推荐方案只表达必要保证，名称/模块归属尚待统一接口表审查：

- 构造时可以失败，必须在 provider 可见之前完成；失败没有已发布资源需要排空。
- 正常同步等待不因 NoMemory、超时或信号中断退出；返回即谓词成立。
- 通知只促使重查，不制造完成；不增加 polling、计数令牌、reset 或异步 Future。
- 等待要求可睡眠上下文且谓词不改变该上下文；违反要求是调用契约 bug，
  不是可恢复硬件停机失败。不自动把现有通用 KResult provider 包装成这种保证。
- host 实现复用 WaitQueue/CompletionWait 的实际无分配机制；test provider
  同样需要证明这一承诺。两种契约不意味着维护两套调度/等待机制。

管理入口在任何不可逆状态改变前检查上下文，非法外部调用返回上下文错误。
进入 remove 后，由驱动遵守同一可睡眠约束，注销使用可靠同步等待。
因此正常 remove 不需要捕获资源失败、循环重试或消费失败绑定；注销的业务
完成契约可以与 Linux 一致，不为低层 KResult 反向设计整个退出模型。

此推荐撤回“只给 unregister 加 KResult 就够了”的候选。对违规调用的具体
诊断必须按 CG-021/CG-024 单独说明；不将仅有 rustdoc 前置条件当作任意 expect
的豁免，也不声称入口检查永久保证后续上下文。这个诊断点与 provider 的
接口归属在完整设计验收前明确，不直接进入编码。

验收重点：构造失败不发布；合法退出无准备分配失败；通知早于等待、虚假唤醒、
多个在途读者均正确；管理入口错误无副作用；旧读取错误行为不受影响。
该方案是 agent 自查后的推荐，不是已获用户验收的新接口。

后续确认记录：用户针对“复用实现、区分读取与可靠退出等待契约”的说明回复
“好的”，确认这一方向；具体接口、诊断方案及整体设计仍未验收，不授权实现。

## 10. D05 probe 回滚与遗漏退出

### Linux 的实际区分

drivers/base/dd.c::really_probe 有两条不同错误路径：

- 驱动 probe 自己返回失败：进入 probe_failed，清理核心建立的关联和 devres，
  不调用该驱动 remove。
- 驱动 probe 已成功，但核心后续添加设备属性等步骤失败：经 dev_groups_failed
  调用 device_remove，再做核心清理。因此不能笼统说“所有 probe 阶段失败都
  不调用 remove”；关键是驱动是否已经成功交付运行状态。

Linux devm_hwrng_register 把 hwrng_unregister 注册为 devres 清理动作。
这是明确交给设备管理资源机制的退出责任，并不是任意消费者最后一次引用
释放时自动推导停机，也不证明每种 Rust Drop 都可以执行完整退出。

### 目标责任表

| 阶段 | 失败/退出责任 | 不允许的行为 |
|---|---|---|
| 仅构造普通资源、尚未对硬件/消费者开放 | 驱动按实际 acquisition 逆序回滚；满足上下文的资源 guard 可正常析构 | 以字段顺序代替硬件访问证明 |
| IRQ 已注册或队列已激活 | 驱动构造路径显式停止相关活动、锁外同步 IRQ，再解除资源 | 因返回 Err 就直接释放可能被硬件访问的内存 |
| hwrng 已注册、probe 尚未返回 | 驱动先停止读者、同步注销，再完成硬件收尾，最后返回 Err | 普通 ? 跳过已注册服务的收尾，等待框架补调 remove |
| probe 已返回成功，模型后续不能接受结果 | 模型仍保有成功 Data，调用正常 remove 后才能丢弃；优先避免不可避免之外的后置失败步骤 | 仅 drop 成功 Data，把它当未初始化对象 |
| 成功绑定正常解绑 | model 调 remove，驱动完成退出，model 随后释放 Data | 消费者引用决定 remove 是否执行 |
| 成功注册凭证未注销便被丢弃 | 生命周期 bug，按统一诊断策略处理 | 宣称自动后台善后是合法正常退出 |

构造回滚建议先用具体驱动的明确错误分支和共同停机 helper，不新增通用
ProbeTransaction 或借助任意 Drop 隐式睡眠。构造状态只表示实际已取得的
资源/注册权；完整 remove 与部分初始化回滚共享能安全调用的具体收尾步骤，
不对缺失资源伪造“成功绑定”。是否后续需要 devm 风格管理接口，另依真实用例
评审，本轮不假设已实现完整 Linux devres。

当前 model/probe.rs 的 stale-success 分支存在直接 drop(data) 的代码；本轮
未证明在当前串行化约束下可达，不将其报告为已复现缺陷。但目标模型不得沿用
这一分支作为成功 probe 与注销竞争时的清理策略，必须按上述成功交付责任处理。

### 验收与状态

失败注入点包括：队列创建、IRQ 注册、排空等待对象准备、hwrng 注册前后、
probe 成功交付后模型后置失败（若设计中存在）。验证无残留可用 provider、
IRQ/DMA 生命周期正确、回滚/正常 remove 不双重执行。
未注销 Drop 与非法 remove 上下文归为同一类契约违约诊断，不自动恢复运行，
具体诊断实现仍待统一定案。不能只打一条日志并声称资源已经安全回收。

D05 的阶段责任已形成候选，诊断策略和实际 VirtIO 退出能力尚不能标记完成。
本轮未修改生产代码，未执行新测试；上述证据来自源码检查和流程推演。

## 11. D06 最终析构审计：不预设 DeferredArc

### 当前可核实的析构链

| 对象 | 现有证据 | 目标退出责任 |
|---|---|---|
| device_res::Irq | Drop 调用 host release_irq，最终进入 kirq 同步注销 | 管理者保活设备，取走 guard 后在合法上下文、锁外释放 |
| VirtIORng/队列/DMA | VirtIORng Drop 调 queue_unset；Dma Drop 调 Hal::dma_dealloc | Ticket 10 明确停机及未完成请求回收后，在驱动退出中释放 |
| HostRngCompletion | 只含 WaitQueue，无自定义睡眠析构；waiter 为栈上借用节点 | 等待返回前解链；排空结束及通知完成后才允许最后对象引用释放 |
| DeviceRef/描述 | BusDeviceData 已要求纯描述、析构无需可睡眠上下文 | 保留该契约，不把 MMIO/DMA/IRQ guard 放进设备描述 |
| provider trait object | 任意实现可以有自己的 Drop，Send+Sync 不能限制析构行为 | 目标 provider 必须单独审计，不由 Arc 自动推导最终上下文安全 |
| 驱动注册对象引用 | 当前 RegisteredDriver 泛型拥有 ops，不能假设其析构总是纯元数据 | 来源保活接口需限定所引用对象的析构契约，或保持其独立管理所有权 |

特别是 IRQ handler 会升级设备 Weak 并持有临时强引用。正常退出中管理者
必须一直保活设备直到同步注销返回，防止 IRQ 回调成为活动设备的最后持有者。
这首先是正确所有权问题，不是给最外层换成 DeferredArc 就能修复的问题。

### 设计结论

普通 Arc 仍是目标 hwrng 的首选，不添加 DeferredArc 前置或默认依赖。
完成显式退出后，旧消费者保留的对象不应再承担 IRQ 同步、队列关闭或 DMA
解除等活动资源清理；这些资源已在退出中解除，最终析构只处理剩余状态。
具体驱动可以用自己的受保护资源状态实现这一点，不要求通用 payload 容器。

这个结论不是宣称所有未来 provider 都可在任意上下文析构：可靠等待 provider、
来源引用、驱动定义引用的析构要求要进入接口契约。如果实际对象确有必须延迟
的最终析构，再局部评估 DeferredArc，并说明为何不能在显式退出中完成。
不把“Send+Sync”误写成“不睡眠 Drop”，也不把 RCU/IRQ 等上下文全部默认为等价。

第 7 节保留驱动定义引用的方案因此增加明确约束：不得借该引用把带硬件资源
或需睡眠析构的驱动 ops 隐藏在普通元信息句柄后面。具体引用表示尚待统一
接口定案，不能提前把任意 Arc<dyn AnyDriver> 直接当成安全来源元数据。

验收应分别观察资源解除时点和对象析构时点：旧句柄保留不延迟前者；最后
句柄释放不重复注销 IRQ、释放队列或影响新绑定；等待退出后无残留栈节点。
当前仅审计了上述实现与契约，尚未对目标改造跑测试，也未证明所有外部实现合规。

D06 结论：未发现必须默认引入 DeferredArc 的依据；明确了最终引用需要遵守
的析构约束。尚未固定的来源/等待接口必须承接这些约束，之后才能建议整体验收。

## 12. D07 真实链路与现有可见接口盘点

### 已有生产链路（不是目标模型已接入的证据）

枚举后端 → EnumerationContext::register_device_with_parent → 旧 kdevice
device_desc_add_with_parent/probe_device_desc → 旧 virtio 驱动匹配 → PCI 或
MMIO transport 激活 → VirtIoRng::try_new → HWRNG.attach_legacy → entropy。
桥接代码 forget 注册凭证，保留内核寿命；未走新 model 的完整解绑/重绑路径。

目标仍为既有设计的 aarch64 QEMU VirtIO MMIO 纵向链路；必须在旧设备注册
之前按已识别的设备事实唯一分流，新模型负责 probe 和全部后续生命周期。
其他 VirtIO 类型保持旧路径，不能通过创建旧影子设备获取目标的资源和身份。

### 两项纠正

1. 平台固件枚举确实读取旧 firmware_match_specs，但对 virtio,mmio 有专门
   匹配分支，随后读取 transport 类型。不能笼统推断删掉旧 RNG 驱动描述就
   一定失去 MMIO 发现。迁移须保留这条实际发现链，并区分设备发现与驱动匹配；
   不据此默认新增一套全局匹配表汇总框架。
2. 命名迁移的 63 项回归日志实际挂载 virtio-rng-pci，证明现有 PCI 桥接回归，
   不证明 MMIO 目标。旧附件的 MMIO DTB 导出仅证明特定配置下的固件事实，
   没有启动内核；两份证据都不能替代目标 MMIO 的真实注册/消费/解绑测试。

### 静态源码可确认的兼容清单

| 接口/设施 | 当前事实 | 本轮迁移要求 |
|---|---|---|
| /dev/random、/dev/urandom | devfs 静态随机节点，调用 entropy 池，不是每 RNG 一个节点 | 保留语义；RNG 解绑不能删除这两个池接口 |
| hwrng provider 对外节点 | 当前检查的 devfs/sysfs/集成代码未找到 /dev/hwrng 或 rng_current/rng_available 实现 | 不把 Linux 的完整 hwrng ABI 作为已经存在的兼容项，也不擅自新增 |
| DeviceNode 投影 | 当前 DeviceNodeKind 只有 Input/Drm；devfs/sysfs 按这两类投影 | 不因删除新 base/class 而破坏旧 input/DRM；不移除旧 kclass/device_node |
| uevent 投影 | kdevice-uevent 处理既有节点类型；旧 core 另有内部生命周期事件 | 区分内部事件与用户可见 uevent，不声称所有内部事件都已暴露为 ABI |
| entropy 来源发现 | 订阅后枚举，按驱动名识别 virtio-rng、按 provider 身份去重 | 保留选择/信任范围和无遗漏发现，不复制驱动名称作为新权威来源 |
| entropy 消费 | 工作者持旧句柄读取，错误后查询状态决定停止/重试 | 注销唤醒并结束已有读取；重绑后必须能选择新实例，不能只验证注册表有条目 |

以上为源码盘点，不是迁移前后运行截图/事件抓取；仍需固定启动配置后的基线
清单和相应验证。解绑结束驱动关联，不得伪造设备消失事件；实际设备注销才
结束注册。没有现成 hwrng 节点不意味着可以省略现有系统接口回归。

### 前置能力及验证责任

- MMIO 描述与 DMA 约束来自真实固件/平台，读设备 ID 区分存在的 RNG 与空槽。
- VirtIO 库按实例后端获得 DMA；显式停机后回收未完成 token，解除映射一次。
- IRQ 采用已合入的同步机制，驱动保活到 handler 排空，不把等读者当作等 IRQ。
- 通过真实 MMIO RNG 消费、保留旧句柄解绑/重绑、两实例隔离及 probe 失败验证。
- 同时回归未迁移 PCI RNG、input/DRM 等实际受影响路径；不假称需要把它们
  全部迁到新模型才能验收，也不以 mock 代替真实目标设备。

D07 结论：发现入口、桥接现状及静态可见接口已形成清单，原证据适用范围已
纠正。精确 MMIO 停机契约、宿主接线接口和运行验收基线仍须进入统一设计；
本轮不执行构建/QEMU，不修改生产代码，也不重新发布 tickets。

## 13. D07 停机与宿主接线的接口级收口

### Linux 证据不能只取一行 reset

- virtio_mmio::vm_reset 写设备状态零；vm_del_vq 另行取消队列配置，
  vm_synchronize_cbs 使用 synchronize_irq，vm_del_vqs 最终释放 IRQ。
- virtio_reset_device 在 CONFIG_VIRTIO_HARDEN_NOTIFICATION 下先标记队列
  broken 并同步回调，再调用 transport reset；它并不自动排空其他业务上下文。
  不能把该条件编译路径误说成所有 Linux 配置都无条件执行相同操作。
- virtqueue_detach_unused_buf 明确禁止用于 active queue，停机/reset 后才
  可以回收未完成 buffer。回收未使用请求和 pop 正常完成是不同语义。

因此前置能力必须分别承诺：无新软件提交、无残留软件回调访问、设备不再 DMA、
未完成请求所有权可回收。reset 的名字或一个写寄存器动作不能替代所有保证。

### 目标 MMIO RNG 的候选收尾顺序（已由第 15 节替代）

1. 驱动在请求锁下设置停止提交状态，锁外唤醒读者；hwrng 排空已有调用。
2. 保持设备和所有队列/DMA 存储有效，抑制设备完成通知；取出 IRQ guard，
   在请求锁之外执行同步注销。抑制通知不作为没有在飞 handler 的证明。
3. 同步注销返回后，软件 handler 已不能再访问设备；由 transport 执行 reset
   并按照其设备/版本契约确认硬件停止。此时无读者/handler 竞争队列状态，
   不需要持禁止睡眠的请求锁跨越可能耗时的停止确认。
4. 仅在设备停止保证成立后回收尚未完成 token、解除对应 DMA 映射；取消
   结果不能作为有效熵。正常完成和取消共享唯一请求所有权，不能双重回收。
5. 释放队列/DMA/MMIO 等资源，再返回 remove。旧消费者只保留停止后的对象。

这是适合当前驱动独立 IRQ guard 的候选接线，不宣称逐行复制 Linux 的
vm_del_vqs 顺序。选择先同步注销再回收，是为了由现有 kirq 保证软件访问结束，
而不是为驱动新增 broken/RCU 回调框架。共享 IRQ 只能撤销本 action，不能
屏蔽其他设备的 line；本设备 pending 原因的清除由 transport 停止契约负责。
最终选择必须覆盖停止期间的 pending/共享 IRQ，不将本段视为已通过硬件测试。

### 各层最小接线契约

| 层 | 输入/输出及责任 | 错误与释放约束 |
|---|---|---|
| 枚举到 model | 已确认存在的 RNG、MMIO/IRQ、设备 DMA 事实及总线/父关系 | 旧注册之前唯一分流；空 slot 不创建 RNG |
| model 到 host | 受约束的当前设备访问上下文 | host 验证资源属于该设备；不依赖全局当前设备 |
| host 到驱动 | 可持有 MMIO guard、该设备 DMA 实例、IRQ 能力、等待能力 | 构造错误在开放业务之前处理；释放与取得的实例配对 |
| 驱动到 VirtIO 库 | transport 与 DMA 后端实例、驱动自有请求 buffer | queue/ring/indirect/request 全部走该实例；旧静态 Hal 路径保留兼容 |
| VirtIO 停机接口 | 已阻止软件提交/回调，输出不可再被设备访问的队列与请求状态 | 不能用正常 pop_used 伪造取消；未确认停止不释放 DMA |
| hwrng 到 entropy | 独立 provider 句柄及发现/撤销语义 | 不暴露裸 runtime，不按设备当前绑定把旧句柄转接到新实例 |

每次资源取得的所有权 guard 记录配对释放事实，不再复制可独立修改的设备
DMA 配置。实例后端不通过 TLS、全局当前设备或为每台设备生成类型来实现。
这些是设计前置契约；实际库扩展在正式源码工作区完成，不修改 registry 缓存。

### 验收与尚缺证据

必须验证无完成消息的 pending 回收、完成/取消竞争、迟到 IRQ、共享 line
其他 action 存活、重复收尾以及映射配对。目标 MMIO transport 的版本、reset
完成判据及可访问窗口仍须从设备规范/目标实现确认；本地 Linux 调用链不是
任意硬件的停止证明。该硬件契约未关闭前不能声称真实解绑已可安全实施。
规范及 entropy 交错的补充核实见第 14 节；不以规范依据替代目标设备验证。

## 14. Reset 规范依据与 entropy 换源缺口

### Reset：已有规范判据，不再只推断 Linux 行为

依据 [VirtIO 1.2 规范](https://docs.oasis-open.org/virtio/virtio/v1.2/virtio-v1.2.html)
的 2.4、3.3.1、4.2.2：设备以状态归零表示 reset 完成，之后在重新初始化前
不得通知或访问队列；驱动应以读到状态零判定完成。MMIO reset 清除中断状态
及队列 ready；停止使用队列还要求写 QueueReady 零并回读同步。未停止的
队列不能直接取回已经交给设备、但设备尚未使用的 buffer。

设计采用完整设备 reset 后的状态回读作为本轮 modern MMIO 停机判据，
不把写零返回或丢弃 transport 当作完成。先确认停止，再执行未完成 token
回收；设备停止与软件 IRQ 排空是两个独立条件，释放前必须同时成立。
该约定针对遵守规范的设备，不承诺故障硬件一定在有限时间内停止，也不能
因等待超时就释放设备仍可能访问的内存。不增加通用可重试 remove 状态机。

当前库 0.13.5 的 transport Drop 仅写状态零，且 RNG 没有公开的 pending
取消接口，不能据此认为前置能力已经具备。需在正式库扩展中提供上述契约。
目标启动配置必须确认 MMIO Version=2；若实际为 legacy Version=1，须另核对
对应契约，不能套用 modern QueueReady 证据或把目标版本检查悄悄省略。

第 13 节“先同步注销 IRQ、再 reset”仍是候选而非最终顺序：通知抑制并不
等同清除已置位的电平中断。统一接口设计需选择能处理 pending 的顺序，
不能靠注销本 action 掩盖仍在驱动共享 line 的设备。规范已给出 reset
清除中断状态的保证，因此优先评估先 reset、后同步注销；前提是 handler
与 reset 的软件访问互斥，且停止后的 handler 不再触碰被重置的队列。
该调整归具体驱动/transport，不进入 model 的通用生命周期协议。

### Entropy：可以从现有代码推导的漏选路径

证据为 util/entropy/src/virtio.rs 的 register_sources、note_device、run：
只订阅 available；替换判断只看 collector 的 is_failed；撤销本身不设置
这一消费者状态；读取失败后 fail 也不重新枚举。由此存在以下交错：

1. A 已被选择，工作者空闲；A 撤销，但 collector 尚未读取、仍未标记失败。
2. B 注册，available 回调因 A 的 is_failed=false 而忽略 B。
3. 后续需求读取 A 失败并标记失败，但不重新发现 B，已有需求也没有转交。
4. 没有下一次注册事件时，注册表已有 B，却不能恢复收集。

这是静态控制流反例，尚未运行复现；不是宣称现有只增不减的启动路径已经
发生故障。但它直接违反目标真实解绑/重绑的验收要求，必须随迁移处理。

### 换源责任与候选处理

- hwrng 保证撤销关闭访问入口、更新注册表，再在注册表锁外通知；消费者
  不需要等一次失败读取才能知道来源已撤销。通知不是延长硬件寿命的许可。
- entropy 订阅可用与撤销，启动仍先订阅后枚举；事件只是重新检查的提示，
  选择以当前可用集合为准，不依赖不同事件回调的执行顺序。
- 撤销只能失效化与事件同一 provider 的选择，A 的迟到回调不能清空 B。
  新候选安装时重新检查当前选择与候选可用性，不能依赖创建 work 前的快照。
- 保留健康且仍可用的当前来源；来源失效时从已注册来源中重选，继续沿用
  virtio-rng 过滤和现有信任策略，不把此次修复变成接受任意 RNG。
- 终止性读取失败也触发重选。尚未满足的采样需求由 entropy 选择层保留并
  交给替代来源，不能随旧 collector 的 has_demand 清零而消失。
- 注销回调不等待/销毁可能还在读取的旧 work，尤其不能在 hwrng 排空之前
  同步 join 旧工作者。锁内换选择、锁外处理工作生命周期；失败工作者也
  不能同步销毁或等待自己。具体 work 持有关系在统一接口收口时明确。

这使用已有发现/撤销能力修正 entropy 自己的选择责任，不引入 model 全局
事件总线、通用代际 ID 或后台自动 remove。

### 必须增加的设计验收场景

| 场景 | 预期 |
|---|---|
| A 空闲撤销，B 随后注册 | 无需先读 A 或第三次注册事件即可选择 B |
| B 已注册，A 后撤销或读取终止失败 | 从当前集合选择 B，而非等待 B 再注册 |
| A 的撤销通知迟于 B 的安装 | 不清空 B，不把旧句柄转接 B |
| A 读取中撤销，已有请求等待熵 | A 读取结束；未满足需求转交 B |
| 候选创建期间又撤销，通知与枚举交错 | 不丢失最终状态；旧候选不可恢复读取 |
| reset 完成延迟，且存在 pending token/IRQ | 停止与 IRQ 排空前保持资源；取消不混入熵 |

本节关闭“reset 没有规范判据”和“换源是否有缺口”的调查问题，不冒充完整
设计验收。剩余收口集中在退出等待契约、来源引用的析构约束、IRQ/reset
访问顺序及 entropy work 交接；不再扩展功能范围，也不开始实现。

## 15. 退出顺序与 entropy 工作者：收敛后的设计候选

本节替代第 13 节的 IRQ/reset 先后顺序及第 14 节尚未确定的工作对象交接。
这是本轮设计结论，未作为已实现或用户已验收记录。

### 驱动收尾：先停止软件访问，再 reset，再同步注销 IRQ

1. remove 保持驱动对象的强引用。在请求锁下置停止状态；之后 read 不再
   读取缓存或提交请求，handler 在访问 transport/queue 之前检查该状态，
   已停止则不访问硬件。锁外唤醒读取者，再同步注销 hwrng、排空业务调用。
2. 请求锁保证置停止状态前正在访问队列的 handler 已离开该访问区间。
   handler 锁外通知的尾部可能仍在执行，因此这里不能声称 IRQ 已排空。
   驱动在锁下取出完整请求资源及 pending 状态，转为 remove 局部独占拥有；
   停止后的共享对象只剩状态与通知对象，不再拥有可由消费者使用的队列。
3. 在请求锁外执行设备 reset 并确认状态归零；整个期间保持 MMIO、队列、
   buffer、DMA 映射及 IRQ guard 有效。reset 清除设备中断原因，不依赖
   屏蔽共享 line，也不把通知抑制误当作已经清除了电平中断。
4. 在请求锁及 irq_guard 锁之外释放本 action 的 IRQ guard，等待在飞
   handler（包括第 2 步的通知尾部）退出。不能卸载共享 IRQ 的其他 action。
5. 此时硬件停止与软件 IRQ 排空均成立，回收 pending token、解除映射并
   释放队列/DMA/MMIO。取消的数据不计入熵；正常完成与取消由同一请求
   状态决定唯一回收方。最后 remove 返回，旧句柄只保留停止后的对象。

这不需要持自旋锁轮询 reset、不需要 RCU/broken 回调框架，也不需要通过
最后一个 Arc 的 Drop 停机。独占取出的是整个资源包，不是从共享对象中
借出 &mut 后在锁外继续使用。回调不得在解锁后保留资源引用；此约束是
具体驱动实现与测试的审查点。若设备拒绝 reset，不能声称可安全释放 DMA。

Linux 对照：本地 drivers/char/hw_random/virtio-rng.c::remove_common 先
阻止读取并唤醒，再 hwrng_unregister、virtio_reset_device、del_vqs。
我们的差异仅是显式处理 Rust 请求资源所有权以及独立 IRQ guard；不是
改变 model 的 remove 契约。停止后 handler 的 NOT_HANDLED 返回不代表
已经撤销 action；最终屏障仍是同步注销。reset 期间资源保活，不承诺坏
硬件的中断风暴或永不完成 reset 有有限延迟上界。

### 工作者归 entropy，而非归每个来源

核对 task/kworkng/src/work_handle.rs 后确认：WorkHandle 的最后 Drop
不等待，由已有 normal work 回收路径排空并销毁捕获对象。因此不能把
“kwork 必须同步 Drop”当成新增机制的理由，也不需要自建退休队列。

比较两种内部组织：保留每来源一个 work 需要处理旧/新工作同时持有需求、
失败回调触发替换及退出窗口；固定一个 entropy 采集 work 则只需切换
HwrngHandle。推荐后者，仍用现有 kwork，不新增线程或执行器。
本地 Linux core.c::hwrng_fillfn 每轮取得当前 rng，提供了“采集执行者不
绑定某个驱动实例”的参考；不照搬 Linux 的常驻填充策略，仍按现有需求采样。

| 对象 | 持有与职责 | 明确不持有 |
|---|---|---|
| entropy 采集工作 | 初始化时创建，随 entropy 子系统存活；串行执行采样/重选 | 某个来源的注册权 |
| 选择状态 | 当前句柄、待满足需求、需重查标记、当前注册实例的终止失败记录 | 驱动资源与硬件停止责任 |
| 一次读取 | 锁外持有当前句柄快照，调用受控 read | 选择状态锁、可跨越注销使用的裸 runtime |
| hwrng 通知 | 更新重查标记并提交固定 work，不等待正在读取的 work | 工作者 join/shutdown |

失败记录按 provider 对象身份匹配，不按设备当前绑定或字符串匹配；只保留
仍注册实例，撤销后清理，避免积累历次重绑记录。它用于保留当前“终止错误
不重启同一实例”的行为，特别是非法返回长度未必使设备 is_failed 变真。
重新注册的是新实例，不受旧记录影响。不向 model 添加失败名单或全局 ID。

初始化必须在 normal work 服务就绪、可睡眠时创建工作；失败不能安装一个
看似可用但无法采样的来源。先准备工作，再订阅可用/撤销，再枚举；通知
和初始枚举均触发同一个重查过程。初始化错误保留现有可观测诊断，不使用
expect 把它当作不可达。此设计不增加 entropy 动态卸载能力。

### 不丢需求、不等待自己的操作规则

- 请求与通知在同一短锁下更新待处理状态并提交已准备的 work；复用现有
  WorkHandle 的 running 时可再挂一次及 AlreadyQueued 合并语义。返回
  Closed 等错误时保留未满足需求并报告，不能清零后当作成功提交。
- 工作者只有在重查标记置位、当前来源失效或首次选择时枚举注册表；正常
  采样不每次全表扫描。枚举不持选择状态锁；安装候选时检查期间是否又有
  通知，有则重新检查。回调锁外执行是 hwrng 的契约，不能反向持注册表锁。
- 工作者在锁下取走一次需求到本次局部责任，再在锁外 read。其他请求
  仍可设置下一次需求；本次成功不能清除期间到来的请求。失败则把未完成
  需求合并回选择状态，终止失败重选，暂时失败沿用现有有退避的重试策略。
- 暂无合适来源时保留需求并结束本次 work，不忙等；后续可用通知再次
  提交它，即使没有新的 getrandom 调用也能继续。无需求时重查不主动采样。
- 撤销通知不取消、join 或 shutdown 这个工作；驱动停止状态和读取唤醒
  使旧 read 返回，随后同一个工作选择 B。旧通知只使状态重查，不能按
  旧快照把 B 清空。撤销与 read 入场竞争仍由 hwrng 的准入保护解决。
- availability 沿用 Available/Failed/TemporarilyUnavailable 的语义：
  可用来源才报 Available；没有来源不伪装成硬件永久失败；终止失败记录
  不阻止新实例恢复。不能因异步选择暂未完成而丢弃已经接受的采样需求。

### 本轮收敛结果及验证边界

退出顺序不再保留“先撤 IRQ 再 reset”两套执行选择；工作交接不再需要
每实例 shutdown/退休协议。测试必须覆盖停止前 handler 已入场、停止后
迟到 IRQ、reset 延迟、共享 IRQ、pending 唯一回收，以及读 A 失败后不靠
第三次注册或新需求即可读 B、运行尾部通知/请求不丢失、同一失败实例不
重新启动。以上是设计推演，未运行新的 UT 或 QEMU。

统一设计还需合并来源引用的析构约束与退出等待接口，随后更新 D01—D07
状态及需求覆盖表，提交完整验收对象；不以这两个局部结论提前进入 tickets。

## 16. 来源引用与可靠退出等待的接口候选

### 来源只引用身份，不延长驱动实现寿命

不能把当前 Arc<dyn AnyDriver> 直接交给来源句柄：RegisteredDriver 拥有
任意 P 类型的 ops，Send + Sync 不保证 ops 的 Drop 不睡眠。为此把驱动
注册的只读身份与可执行实现分开，而不是强制所有未来 ops 都有简单析构。

| 对象 | 拥有内容 | 生命周期 |
|---|---|---|
| 驱动只读身份 | 驱动名称的唯一运行期存放位置；没有 ops、设备资源或退出动作 | 可被旧来源引用延长 |
| 驱动注册实现 | 只读身份引用、匹配表、ops、模型内部注册 bookkeeping | 由模型注册和绑定管理，不由消费者保活 |
| provider 来源 | DeviceRef 与本次注册对应的只读驱动身份引用 | 随 provider；不引用绑定 Data |

DriverDesc 仍可作为注册输入；构造注册对象时拆分输入，不再把带 name 的
完整 DriverDesc 与另一份身份同时存储。注册实现的 name 查询也从该身份
读取，不保留第二个独立可修改名称。只读身份使用普通 Arc；具体类型名
在整体验收时作为命名候选展示，不在这一轮偷偷改现有公开名称。

该对象不是驱动模块卸载 pin，也不是可操作 DriverRef，不暴露 probe/remove。
当前驱动名为 &'static str，身份对象不持有可卸载代码或带析构的扩展 payload。
本轮不承诺动态模块卸载；将来支持时另定义代码/字符串存储的保活责任。
设备位置继续取自 DeviceRef；设备当前驱动查询沿当前关联，旧 provider
查询沿自身只读身份。两者共享身份对象，不共享可变的绑定关联。

这样最终释放旧 provider 不会顺带释放任意 ops；结合第 15 节显式取走
硬件资源，当前目标不需要 DeferredArc。等待适配器、设备描述及停止后
runtime 的最终析构仍分别遵守不睡眠契约，不能仅凭 Arc 推断这一点。

### 等待接口：契约收窄，而非再实现同步原语

可靠排空契约放在 hwrng 的 completion mod：目前只有 hwrng 生命周期需要
它，不为了一个消费者新建 crate 或往 os-api 塞一组未使用的同步接口。
暂称“排空等待能力”，不将此描述视为已确认的 Rust 类型命名。

| 操作 | 合同 |
|---|---|
| 构造/注入 | provider 可见前完成可能失败的准备；失败不留下已发布条目 |
| 检查等待上下文 | 查询当前调用者是否可睡眠；无状态改变，不是永久有效凭证 |
| 谓词等待 | 合法上下文无分配失败、超时或信号取消；成功返回意味着谓词成立 |
| 通知 | IRQ 可调用、不睡眠；状态先发布，通知仅促使重查 |
| 析构 | 等待节点解链后无需睡眠；不在析构中自动等待读者 |

等待入口允许报告非法上下文，但错误集合只表示上下文违约，不接受 NoMemory
等正常资源失败。host 复用现有 WaitQueue/CompletionWait；读等待与排空
等待可以由同一具体实现类型提供，但使用不同队列实例，且不能把任意
RngCompletion 直接适配成可靠排空能力。现有 read 的 NoMemory 测试保留。

model 在 DeviceServices 上增加最小可睡眠上下文查询，由 host 调 ktask
实现；不引入 ktask 依赖，也不为一个布尔查询建立可转移执行凭证。设备
管理入口先验证，再获取睡眠管理锁/改变生命周期；非法入口返回错误且
不调用 probe/remove。具体管理错误类型沿用现有错误体系，不静默忽略。

### 公开拒绝与内部违约必须分开

公开 hwrng 注销保留唯一凭证的可变借用及错误返回：入口检查不通过时
凭证、注册表和准入状态不变。正常路径先关准入并撤下条目，锁外通知及
等待，再标记注销完成。若内部 callback/provider 破坏上下文合同，不能
因为等待失败就标记完成、消费凭证或让驱动继续释放硬件资源；已经关闭
的准入也不回滚为可用。这是违约现场，不是可支持的 remove 重试状态机。

void remove 的成立依据不是签名抹掉错误，而是实现约束：它在验证过的
管理上下文中运行，排空前已释放所有禁止睡眠的锁，通知回调恢复调用上下文，
可靠等待不引入资源失败。在这些条件下注销不会返回错误。具体驱动的
每条 remove/rollback 路径必须验证这些条件，而不是对任意 KResult unwrap。

仍需要明确的诊断决策：若上述内部合同被破坏，或成功注册凭证未经注销
就 Drop，推荐停止该错误执行路径，不能打印日志后继续释放；不增加自动
后台退出或无界泄漏作为正常语义。任何 fail-fast 站点必须按 CG-021/024
给出该实现的具体不变量及实施证据，只写“调用者应当正确”不足以豁免。
本轮没有将该推荐记作已满足规则，也没有添加 panic/expect 或 crate 级例外。

这项诊断尚不能仅靠接口表判定完成：须在最终设计中明确哪些站点确属内部
不变量、哪些仍能由外部非法调用到达。后者必须保留错误返回，不能混用
“普通错误”和“bug”规避规则。若无法证明某站点，不得以 void remove 为由
硬加断言；应在进入不可逆动作之前修正调用边界。

已有候选，D05 的合法回滚责任已确定。剩余验收缺口集中为违约诊断边界，
以及第 4 节 R01/R04 管理串行化与延后探测的现有代码映射；不能因解决了
hwrng 的局部问题就把整个模型标为已验收。下一轮按这几个确定项目做最终
一致性核对，不扩展新机制、不进入实现票。

## 17. R01/R04 代码映射：单设备管理与探测调度分开

### 两个职责不能共用一个“正在探测”标记

当前 domain/probe.rs 由全域 probing 标记串行执行 probe pump；这不是目标
单设备管理锁。当前 lifecycle.rs 的 remove_device 同时承担停止、递归孩子、
删除设备以及 remove_retryable 恢复，也不是目标“解绑不注销”的实现。
这些旧实现必须迁移，不能把既有 UT 通过直接记作 R01/R08 已覆盖。

目标管理规则保持为：同一设备的 probe、unbind、unregister 在同一睡眠
管理锁下串行；等待锁后复核注册及绑定状态，不能仅相信入队时快照。回调
不持全局注册表/调度自旋锁。锁和必要等待能力在设备可见前准备；host
通过可移植契约提供，不允许 model 为此直接依赖 ktask/ksync。现有
DeviceServices 尚无该锁能力，属于必须落实的前置接口，不是假定已有。

成功 probe 的 Data 在该管理临界区内交付；随后竞争的 unregister 取得
锁并调用 remove，因此不需要“过期成功结果直接 drop”的正常分支。若
模型有成功 probe 后仍会失败的提交步骤，必须显式 remove 后回滚（第 10 节）。
unbind 保留设备注册并解除当前驱动；unregister 关闭调度资格并撤销注册。
队列里遗留的设备引用只保活对象，取得管理锁后发现已注销就跳过，不能复活。
不恢复按 parent 自动递归卸载、整树准备或通用 remove_retryable 状态。

### 延后探测有两种不同的漏唤醒窗口

第一种是“依赖已通知，设备才登记 Deferred”。当前 dependency.rs 的
dep_generations/dep_seen_generations 用于处理这个窗口。本地 Linux
drivers/base/dd.c::driver_probe_device 同样比较 probe 前后的
deferred_trigger_count，登记 deferred 后在有变化时重新触发。
这是进度版本，不是设备身份；没有理由把它作为公开 ID 或直接删掉。
目标保留这项保证：probe 前记观察点，登记与比较和 wake 更新使用同一
调度保护；通知发生在登记之后则由 wake 摘取等待者。具体按依赖记录的
现有行为不因本轮迁移扩展成每次通知都重跑所有驱动。

第二种是“工作已入队，但探测执行者正在退出”。现有代码有可推导反例：

1. A 的 select_batch 取到空队列，并取走 pump_requested=false，决定退出。
2. B 入队并调用 probe_pending；看到 probing=true，只设 pump_requested=true。
3. A 的 ProbePumpGuard::drop 只把 probing 改成 false，未再检查请求或队列。
4. B 已返回，A 也返回；pending 工作和请求标记仍在，但没有执行者负责处理。

该结论来自 probe.rs 的退出路径、mod.rs 的 guard Drop 及 dependency.rs
的相同触发方式；未运行并发复现，不报告为已观察到的启动故障。它说明第一种
窗口的代次保护不能替代第二种窗口的调度握手。

### 最小修正方向，不增加第三套事件机制

pending 的入队、执行权认领和空队列时执行权释放由同一短锁保护。执行者
只有在锁内确认无待处理工作时才把 running 清零；生产者在同一锁下入队，
若没有执行者就取得/提交执行责任，否则由当前执行者后续取队列。回调仍
在锁外运行，不能用“全程持锁”换掉竞态。正常退出不再靠 guard Drop 独立
清标记；若保留异常退出 guard，必须与正常交接明确区分，不能清掉后来
执行者已取得的所有权。

这解决的是执行权交接，不授权全局串行设备回调。目标按设备管理锁串行，
调度队列只负责派发；不能为了现有单槽 host 资源收集器而保留全域 probe
互斥。真实资源必须通过本次设备访问/实例能力交付，不依赖全局“当前 probe”。

验收需要确定性暂停点而非概率压力：A 最后一次空队列检查前后分别让 B
入队；通知在 probe 检查前、检查后登记前、登记后分别发生；执行候选出队
后注销设备。分别验证无需第三次外部通知也能推进、没有重复并发 probe、
注销后迟到工作不调用驱动。管理并发另测两设备互不阻塞及同设备清理一次。

本轮仅记录反例和目标设计，不修改生产代码。尚未完成的管理锁宿主接口及
第 16 节违约诊断必须作为明确验收项保留，不能用“参照 Linux”四字带过。

## 18. 管理锁接口候选与需要明确的故障策略

### 管理锁：复用宿主 mutex，模型不实现锁算法

锁契约是 model 内部管理所需能力，放在 model 的宿主服务接口模块；具体
驱动只收到 DeviceAccess，不取得管理锁，也不能解锁。host 构造每设备独立
锁对象，在设备注册前完成准备，由设备管理对象持有到管理活动结束。

采用对象安全的回调式入口（以下为接口形状，不冻结类型命名）：

```text
run_locked(&self, operation: &mut dyn FnMut()) -> Result<(), ManagementError>
```

保证：合法调用取得锁后同步执行一次 operation；返回前释放锁，不保留回调。
非法上下文及同任务重入在调用 operation 前返回错误。回调借用栈上结果槽
传出 probe/remove 的结果，不需要每次分配 Box<dyn Guard>，也不暴露可被
随意 unlock 或转移到另一任务的原始锁。host 以局部 RAII mutex guard 保证
正常返回/支持展开的测试路径解锁；不把 callback 自身结果混入锁错误。

X-Kernel adapter 使用现有 ksync::Mutex<()>：上下文查询拒绝非法调用，
现有 RawMutex::is_owned_by_current 可拒绝同锁重入，不在 model 新建任务
ID 或自动绕锁。取得锁之后复核设备注册/绑定状态；注册表短锁不跨回调。
驱动违反约定不返回、主动退出当前任务或跨设备形成锁环，不是该接口可以
自动恢复的正常情况。多设备锁顺序仍归实际总线/调用链，不提供通用整树事务。

### 当前 mutex 的分配事实与范围边界

task/ksync/src/mutex.rs 的竞争路径仍调用 block_on(listener)，后者在
task/ktask/src/future/mod.rs 中调用 KWaker::new，以 Arc::new 分配唤醒对象。
已合入的 Completion 改造没有迁移这个调用链。因此不能声称复用现有 mutex
后整个设备管理过程无分配；目前只承诺第 16 节排空等待的登记不分配。

这一分配发生在管理锁获取阶段、执行本次生命周期操作之前；现有分配遵循
内核 OOM 策略，不能伪装成管理接口已经能够返回 NoMemory。当前 R08 要求
可睡眠和正确串行化，没有要求整个 probe/remove 路径零分配。本设计暂不
因此扩展为 mutex 重构，也没有证据断言这条路径已经形成分配锁死锁。
若将“管理锁竞争也不分配”纳入本轮要求，应明确列为 ksync 前置改造，使用
已完成的同步等待基础；不能在 driver-model 内复制一个替代 mutex。

### 故障策略：不能以“bug”代替可执行决策

| 情形 | 候选行为 |
|---|---|
| 外部在不可睡眠上下文调用管理入口/注销 | 返回明确错误，不进入回调、不撤下注册、不释放资源 |
| 同任务再次进入同设备管理 | 获取锁前返回重入错误，不默默绕锁、不主动制造自死锁 |
| probe 或资源构造正常失败 | 显式回滚，返回错误，禁止 panic |
| 合法上下文的正常排空等待 | 完成后返回，无 NoMemory/超时/信号取消分支 |
| 回调破坏上下文，导致已开始退出不能继续 | 内部生命周期违约，不能忽略错误继续释放；致命诊断为待确认候选 |
| 已成功发布的凭证未经注销便 Drop | 生命周期违约；致命诊断为待确认候选，不自动后台退出 |

最后两项是行为决策，不是假称永不可达：安全 Rust 调用者确实可能错误地
drop 凭证，驱动实现也可能违反上下文合同。若采用致命诊断，必须明确其
条件、影响与本地 lint 规则适用理由；不能使用“proven unreachable”作为
不实豁免。当前 kruntime 的 panic handler 最终 platform_power_off，故
“fail-fast”不是只结束这一驱动调用，可能终止整个内核运行。

此前推荐把这两类生命周期违约统一作为致命错误处理；经用户要求核对 Linux
后撤回该默认推荐，理由见第 19 节。普通调用错误仍走 Result；不能用“这是
bug”代替具体错误路径分析，或仅靠整体方向确认新增 panic。

本节已给出管理锁的具体接线及分配限制。违约处理仍需按第 19 节修订，
不是请求用户批准一个被误认为与 Linux 对齐的默认致命策略。

## 19. Linux 对照纠正：生命周期违约不等于统一 panic

用户追问“策略和 Linux 对齐吗”后核实本地 /root/linux-stable：

- drivers/char/hw_random/core.c::hwrng_unregister 撤下条目、切换来源并
  wait_for_completion；它没有将非法上下文统一转换成 Result，也没有
  显式的统一违约 panic 策略。调用者必须遵守可睡眠和生命周期约定。
- kernel/sched/completion.c 的等待入口调用 might_sleep；调度调试开启时，
  kernel/sched/core.c::__might_resched 对非法上下文输出诊断、栈和 taint，
  该路径本身不是无条件 panic。其它告警/调度错误和 panic_on_warn、
  panic_on_taint 等策略可能影响结果，不能概括为 Linux 永远不会 panic。
- devm_hwrng_register 通过 devres 注册 hwrng_unregister 清理动作；普通
  hwrng_register 则由调用方负责显式注销。Linux 没有与我们唯一 Rust
  注册凭证 Drop 完全相同的入口，不能宣称遗漏注销必定被检测并停机。
- drivers/base/core.c::device_unregister 明确先 device_del 再 put_device；
  lib/kobject.c 的最终释放甚至会补做残留 sysfs 删除。这只是具体对象的
  清理语义，既不是统一 fatal，也不证明可以替任意驱动完成硬件停机。

因此应对齐的是正常退出的责任与顺序，不是把所有调用错误升级成整机停止。
我们在管理入口用 Result 拒绝非法上下文属于显式防御性差异；统一对遗漏
注销及回调违约 panic 属于更强且尚无逐点依据的策略，撤回其默认推荐。

后续应先把注册权固定在绑定/明确管理资源的所有权链中，验证成功、失败、
解绑所有正常路径都会注销。真正剩余的违约逐项规定诊断和安全后果，不能
把“警告后继续释放活动资源”当 Linux 模型，也不能将具体 devres 自动清理
偷换成消费者 Drop 或任意上下文自动 remove。本节只纠正策略结论，不
宣称这些违约的具体 Rust 处理已完成设计，不新增实现或 lint 例外。

## 20. 当前 hwrng 的清理链：选择显式 remove，不提前实现完整 devres

进一步核对 Linux virtio-rng.c::remove_common：该驱动自己先标记移除、
唤醒读取，再显式 hwrng_unregister，最后 reset/del_vqs。虽然 hwrng core
另有 devm 接口，这条具体路径并不靠通用 devres 自动推导硬件退出顺序。
devres_release_all 本身在短锁内摘取资源，锁外执行释放动作；不能把它
误译为任意对象析构时都允许同步等待。

因此当前唯一真实迁移对象采用显式清理，与 Linux VirtIO RNG 的流程对齐：

```text
model 的当前绑定
  └─ 具体驱动的 Data（唯一管理所有者）
       ├─ HwrngRegistration（唯一注销权）
       └─ 驱动运行对象的强引用（保活到 IRQ 同步结束）

entropy / 其他消费者
  └─ HwrngHandle（读取权，不持有注册凭证或绑定 Data）
```

Data 的字段及退出 helper 是具体驱动私有实现，model 不认识其中的 hwrng
凭证。运行对象拥有 read/IRQ 所需资源；不要把消费者仍可访问的资源 guard
另放在不受其生命周期约束的临时对象里。remove 调用共同退出 helper，依
第 15 节停止读者、注销服务、停止设备、同步 IRQ 和释放资源，随后 model
才释放 Data。消费者最后 Drop 不触发这一流程。

probe 在发布前准备所有正常可能失败的资源，尽量把 hwrng 注册放在最后；
这减少回滚分支，不意味着注册后失败可以被禁止或忽略。若发布后仍失败，
probe 自己调用同一退出 helper 再返回 Err；已返回成功的 Data 若不能被
模型接纳，模型调用 remove 后再丢弃。失败前取得了哪些资源，就收尾哪些，
不伪造完整注册，也不对未完成构造的对象调用完整 remove。

当前不新增通用清理动作栈、devm crate、后台退出或自动 Drop 注销。以后
有多个真实驱动需要 devm 时，可以引入设备管理的清理动作；那时必须明确
动作注册失败回滚、逆序执行与驱动自有停机的关系，不能先做空框架。

这条清理链能使正常路径的退出责任明确，但并不在类型层面证明任意驱动
实现永远不遗漏注销。不能据此把 HwrngRegistration 的遗漏 Drop 写成
“不可达”。其通用 API 的违约安全后果仍需单独收口；本节不引入默认
panic，也不把泄漏或带活动硬件释放宣称为已接受的恢复策略。

验证落点为驱动生命周期测试：正常解绑、各构造失败点、注册后失败、成功
交付后模型拒绝、重复解绑及持旧句柄重绑，检查注销、IRQ 解除及 DMA 回收
次数和先后顺序。仅检查 Data 被 drop 不构成退出成功证据。

## 21. 遗漏注销的最小语义候选：注册不随凭证 Drop 消失

当前 class.rs 的集合持有 Publication，后者强引用 Inner/runtime；注册凭证
是管理权，不是运行对象唯一内存所有者。目标 hwrng 保留这种注册表强所有权，
但不保留当前 Registration::drop 自动调用 withdraw 的行为。

候选规则如下：

- 成功 register 后，注册表独立保活 provider 及其 runtime，直到显式
  unregister 按同步协议完成。丢弃注册凭证不等于 unregister。
- 凭证已成功注销时，Drop 只释放凭证自身的普通引用。
- 凭证尚未注销时，Drop 可作与上下文相容的违约诊断，但不等待、不调用
  runtime/hook、不改注册表，不宣称已经关闭或排空。保留 must_use 提示。
- 不另加“孤儿表”、隔离状态、扫描回收线程或自动 remove。现有表项仍在，
  所以保活自然继续；显式泄漏凭证也不会使活动 runtime 被提前析构。

这意味着遗漏注销确实可能造成残留注册、资源泄漏和仍可发现的旧来源；它
是需要修复的驱动 bug，不是成功退出或可接受的正常恢复。与 Linux 普通
hwrng_register 需要调用方注销的责任一致，但强引用保活是我们的 Rust
所有权设计，不能说 Linux 的链表本身提供了等价内存安全保证。

这一规则只保证“凭证 Drop 不主动释放运行对象”，不能保证任意驱动错误
都安全：runtime 必须真正拥有其 read/IRQ 可访问的资源，不能仅强引用
壳对象而把 MMIO/DMA guard 留在已被释放的 Data 中；父控制器被错误拆除、
驱动绕过协议主动释放资源等仍是驱动/总线的安全责任。针对当前 VirtIO
迁移，第 15/20 节已要求资源包归 runtime，Data 只持管理权与强引用。

该方案明确放弃“遗漏注销时框架仍保证整个设备正常解绑”的承诺；model
不能从通用 Data 推断所有子系统注册，也不能把 remove 返回视为已经检测
所有违约。正常实现必须通过共同退出 helper 与失败注入验收保证职责履行。
若需要自动保证，应该另设计真正的设备管理清理动作，而不是把隐式同步
退出藏在普通 Drop 中；当前不扩展该机制。

### 注销错误边界不因这个候选变化

公开注销在非法上下文中先拒绝，保持凭证及注册不变。可靠等待在符合合同
的退出路径中没有普通资源失败；回调不得破坏调用上下文。如果任意外部
回调能正常导致排空中途失败，说明接口边界仍有缺陷，不能用凭证 Drop
作为补救，也不能把闭合后未排空当成功。这一点仍需接口实现的逐点验证。

### 验证与决策状态

遗漏注销用例应检查：无同步等待、无自动 withdraw、无资源提前析构，且
注册残留被明确观察到；正常注销用例检查表项撤下、资源退出和旧句柄不可
继续读取。泄漏测试使用可控测试夹具回收，不把测试专用清理入口暴露给生产。
提出时为最小语义候选；随后在对话中完整说明上述 Drop 行为及残留后果，
并明确询问“你认可这个明确的 Drop 语义吗？”，用户回复“好的”。据此
确认本节注册所有权及 Drop 语义，不再重复请求该项批准；不将确认扩展为
真实设备全链路已验收。后续设计收口不再围绕遗漏注销增加异常退出框架。

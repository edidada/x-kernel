实现调查基线：`491cb6e8d`；本文是未提交的需求候选，不是该提交的内容。

## 1. 问题与目标

当前新模型尚未完成真实驱动的生产接入，注册、绑定、资源和退出责任仍需整理。
继续只调整类型名和字段，无法证明框架在失败、解绑及重新绑定时成立。

本阶段目标是明确核心驱动框架的行为和责任，以真实 hwrng 完整链路验证。
优先保证设备、资源、退出责任正确，其次保证扩展性。已有能力的模型参考
Linux 的概念与生命周期，不要求复制其 C 接口或补齐全部功能。

允许适配、重构内部接口；迁移时不得丢失已有正确功能。不要求本阶段迁移
所有驱动，也不预先决定必须重写哪些 crate。

## 2. 使用者与术语

- 枚举方：发现并注册设备，提供总线归属和设备描述。
- 总线实现者：提供本总线的描述语义与匹配规则。
- 驱动作者：绑定设备，申请运行资源，发布能力，负责相应退出收尾。
- 子系统和消费者：获得设备能力，并遵守使用与撤销契约。
- 宿主适配者：实现 OS 能力，接入现有系统设施。
- 集成维护者：迁移设备，验证新旧路径兼容及故障恢复。

设备注册、驱动绑定、驱动解绑、设备注销和对象引用存活是不同概念。
解绑结束当前驱动与设备的管理关系，不等于硬件拔出；注销结束设备注册。
保留对象引用不等于仍有硬件操作权限。具体术语见
[设备模型术语](../../../drivers/base/model/CONTEXT.md)。

## 3. 功能需求与验收

下列行为是对已确认意图的可验收细化，待随本文整体审阅。
验收描述不指定内部结构、锁类型或测试专用生产接口。

### R01 注册与绑定分离

来源：Q5、Q7、Q8。
设备可在没有成功绑定驱动时存在；解绑保留设备身份及注册关系，允许再次绑定。
注销后不得对该已注销对象重新绑定；旧引用不能恢复其运行权限。
验收：无匹配驱动、绑定、解绑、再次绑定、注销各阶段可区分；跨解绑持有的
设备引用仍指向同一设备，跨注销保留引用不会使设备恢复可操作。

### R02 设备事实与责任明确

来源：此前 review 约定、Q1、Q7，以及仓库所有权边界规则。
设备描述、总线归属、父子关系及发布来源各有明确权威来源，不能依靠多个
可独立变化的副本决定同一事实。总线类型、具体总线实例、父关系不能混为一谈。
允许有明确用途和失效语义的快照或缓存，不为内部索引需要强加公共身份接口。
验收：从设备、驱动回调和发布查询同一事实时一致；审查每项关系由谁建立、
维护和终止，不能把持有引用自动解释为拥有绑定资源。

### R03 绑定资源及失败回滚

来源：Q5、Q11。
每次绑定获得的资源与发布具有明确生命周期；probe 中途失败不能留下仍可
使用的失败绑定能力。解绑完成后该次绑定的运行职责已经结束，可以重新绑定。
验收：在资源申请和能力发布之后注入 probe 失败，检查发布撤销、资源清理
及后续重试；重复绑定/解绑不重复释放或无界积累已结束绑定的资源。

### R04 延后探测与恢复

来源：Q11。
依赖尚未就绪与普通失败可区分；条件满足后可以重试，并且不会因通知与等待
登记交错而永久错过恢复机会。注销后不能被迟到的依赖通知重新启动。
验收：依赖在探测前、等待后及两者交错时到达，分别验证最终恢复；覆盖等待中注销。
这不要求本阶段建立没有实际使用者的通用依赖框架。

### R05 发布与绑定代际隔离

来源：Q9、Q11。
绑定退出或失败后，旧消费者句柄不能访问后续绑定的资源；重新绑定不能使旧
发布复活。消费者持有句柄不代表拥有注册或阻止解绑的权利。
验收：保留旧句柄经历解绑和重新绑定，旧句柄不能开始新的硬件操作，新发布可正常使用。

### R06 在途操作安全退出

来源：Q8、Q11。
退出必须阻止新的不合法操作，并安全完成或取消已经开始的操作；不能在操作
仍依赖资源时释放这些资源。驱动、子系统和框架的收尾责任必须明确，不能假定
通用核心自动终止任意驱动活动，也不能等待所有纯元数据引用消失才允许解绑。
验收：确定性构造操作进行中与解绑交错，验证停止准入、唤醒或完成、资源释放
的顺序；退出后保留元数据引用不恢复运行能力。不可恢复硬件故障不承诺固定退出时限。

### R07 多实例隔离

来源：Q9。
同一个驱动可以绑定多个设备，多个 hwrng 实例可以分别发布。解绑或注销其中
一个不得撤销其他设备的资源和发布；重新绑定不得混用其他实例或旧绑定的资源。
验收：至少两个实例共同运行，退出一个时另一个仍能提供能力，再绑定后来源及资源不串用。

### R08 管理并发与上下文

来源：Q11、Q12；Linux 核对见进度记录。
普通 probe/remove、解绑、注销遵守可睡眠任务上下文的要求；不能从禁止睡眠
的上下文直接执行完整流程。同一设备的管理操作不得取得相互冲突的生命周期
所有权；重复或竞争请求必须有可解释的结果，不能重复清理或在退出后重新发布。
允许回调睡眠不等于允许生命周期重入；不得等待必须取得当前所持锁才能结束的操作。
最终对象释放和 IRQ 回调的上下文另行明确，不套用普通 remove 的保证。
验收：交错 probe、解绑、注销及重复请求，验证结果和清理次数；审查真实调用
路径的上下文、锁与等待条件。具体串行化方式、错误类型由设计说明。

### R09 可移植边界

来源：仓库 `docs/ai/driver-subsystem-boundaries.md` 硬规则、Q1、Q6。
具体可复用驱动通过契约获得 MMIO、IRQ、DMA 等 OS 能力，不直接依赖宿主内核
实现；宿主适配层实现契约，子系统定义对外设备能力。设备相关请求必须关联
正确的设备及其约束。通用模型不承接具体家族的命名和硬件策略。
验收：真实 hwrng 调用链和依赖方向符合规则；资源失败与释放行为在宿主边界可验证。

### R10 真实 hwrng 完整接入

来源：Q3、Q4、Q10。
至少一条真实 hwrng 路径经过新模型的发现/注册、匹配/probe、真实 OS 能力、
class 发布和 entropy 消费。仅使用旧模型加新 class 桥接不能算完成。
验收：证明实际能力由新模型管理的绑定产生，并验证正常消费及真实路径的
解绑、重新绑定和注销；可控失败和竞态另以模型/消费者测试补足，不用 mock 替代真实接入。

### R11 渐进迁移与现有功能保持

来源：Q2、Q10。
新旧路径可以并存，但同一个设备不能被两套模型同时绑定、发布或清理。
本阶段迁移一条真实 hwrng 链路；其他已有驱动可留在旧路径，后续迁移允许改
适配代码，但不能丢失正确功能。迁移过程不得破坏未迁移设备。
验收：目标设备只有一个生命周期管理者；执行迁移链路及未迁移路径的相关回归。

### R12 现有系统接口兼容

来源：Q13 及用户对源码核对结论的确认。
sysfs/uevent 已有真实接入，不能整体排除在迁移兼容要求之外。迁移影响到的
设备节点、投影和事件行为必须盘点并保留；不得将解绑错误表达为设备注销。
不因此要求补齐 Linux 全套管理 ABI，也不要求本阶段重写这些系统设施。
验收：对迁移前实际存在的节点、属性和事件建立清单，检查迁移后行为；对于
新支持的解绑和注销，分别检查绑定关系变化和设备消失的语义。具体基线清单由集成调查给出。

### R13 扩展但不提前实现

来源：Q6、Q7、Q13。
当前没有实际使用的能力需考虑后续接入空间，但不提前实现。当前未找到实际
驱动 PM 调用链、物理热插拔事件接入或动态模块装卸支持，故本阶段不实现这些
完整机制。不能删除既有的局部行为，例如现有定时器恢复处理。
验收：设计审查说明未来能力的责任落点及是否需要侵入核心；不以空接口数量
作为扩展性证明。若后续调查发现实际使用，更新兼容清单，不能静默归为非目标。

## 4. 验收组织建议

以下入口供随本文评审，不代表测试已经执行：

1. 模型公开行为：注册、匹配、失败、依赖恢复、解绑、再次绑定、注销及多实例。
   使用测试宿主和确定性同步制造失败/竞争，不依赖内部字段布局。
2. class 消费者行为：旧句柄隔离、操作准入、在途收尾及实例互不干扰。
3. 真实 hwrng 集成：运行真实设备路径并消费熵，检查资源、节点和事件的实际来源。
4. 架构 review：职责、单一事实来源、所有权、上下文与宿主边界。UT 通过不能替代它。

沿用仓库外置 UT、Kconfig/Make 验证和文档同步要求。没有指定吞吐、延迟阈值，
不虚构性能验收；重复生命周期的资源增长属于正确性检查。

- 未确定 Rust 类型、crate 拆分、状态枚举、锁、引用表示及 ID 方案。
- 不预设所有现有 model/class/os-api 接口必须保留，也不预设必须重写。
- 真实 hwrng 的具体平台/传输路径及现有节点事件清单仍需在集成设计中核实并展示；
  “至少一条完整真实链路”已经确认，不偷换为全平台迁移或仅 UT 验收。
- 拓扑、控制器/provider 的现有使用与退出责任须在设计中核对；若需要缩减
  已有正确能力或新增可观察限制，必须回到需求评审，不得自行加叶子限制。
- 具体 API 错误分类、匹配/重试策略、绑定退出与子对象的协调由设计给出，需满足
  上述行为与 Linux 参考约束；需要改变需求时单独说明差异。
- tickets 落点和实现切片在设计之后确定，本轮不发布外部 issue。

## 6. 设计质量约束

来源：用户补充要求“在满足功能需求前提下……模块设计要清楚，关系是什么，边界是什么，名字要表达清楚”。
这不是以功能测试通过即可豁免的可选优化，设计评审须逐项说明：

- 职责：每个模块解决什么问题、对谁提供什么能力，以及明确不负责什么。
- 关系：模块之间的依赖、调用、拥有与借用分别是什么；不能用一张无语义箭头图代替说明。
- 边界：谁维护事实和状态，谁建立和终止对象/关系，谁执行失败与退出收尾；跨边界契约及上下文明确。
- 命名：名称表达领域角色和生命周期责任，不依靠含糊的包装层名称掩盖职责；新增概念必须说明与已有概念的区别。
- 聚合：按功能、状态、不变量和生命周期聚合模块；仅属内部实现细节的内容不为拆分而公开，crate 划分须满足仓库所有权边界规则。
- 必要性：对新增对象、持久字段及包装层说明其用途、权威来源与存续期，避免重复保存同一事实或仅透传 API 的无意义层次。

评审材料应先展示职责表、关系及生命周期，再展示必要的核心类型和命名依据。
用户不需要逐字段提供设计；agent 负责推导与自查，存在功能取舍或需求冲突时才回到需求确认。

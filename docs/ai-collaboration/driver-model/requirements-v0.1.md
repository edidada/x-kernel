# 新驱动框架模型需求 v0.1

状态：需求候选，待人工确认。不是实现设计，不授权开始编码。
现状基线：`491cb6e8d`。对应代码、已讨论的设计建议和本需求候选不可混为一谈。

## 1. 问题与目标

框架维护者需要一个职责清楚、可由真实驱动验证的设备模型。当前新旧实现均未
充分区分设备注册与驱动绑定；新 model 尚无生产宿主适配与真实驱动闭环。
仅继续改字段与名称，不能证明所有权、退出、重新绑定及迁移方案成立。

本轮目标不是重写整个驱动子系统，而是重新确定模型的外部行为与职责，
根据需求选取设计，再以可独立验收的纵向 tickets 实施。
既有实现可以复用，但“现在这样写”不是必须保留某种行为的理由。

## 3. 使用者与使用场景

1. 作为枚举方，我希望先注册一个设备，即使尚无驱动匹配，也能稳定识别它。
2. 作为总线实现者，我希望定义本总线的设备描述与匹配规则，而不把家族细节塞入通用模型。
3. 作为驱动作者，我希望使用所驱动设备的资源与能力，不依赖具体宿主内核实现。
4. 作为驱动作者，我希望 probe 部分失败时已取得的资源和发布有明确的回滚责任。
5. 作为设备管理者，我希望解除绑定而不伪造一次硬件拔出和重新插入。
6. 作为设备管理者，我希望显式重新探测同一设备，而不是更换设备身份。
7. 作为能力消费者，我希望旧发布关闭后不会因设备重新绑定而恢复可用。
8. 作为资源持有者，我希望停止接收新操作时，已有操作仍按规定安全结束。
9. 作为子设备枚举方，我希望父设备与所属总线的约束一致，不把设备挂接到已经退出的来源。
10. 作为宿主适配者，我希望明确哪些服务由宿主提供，哪些生命周期由框架负责。
11. 作为集成维护者，我希望迁移一台设备时只有一个生命周期管理者，其余旧设备保持工作。
12. 作为评审者，我希望需求、设计和测试之间可以追溯，不以 mock UT 代替真实设备验收。

## 4. 系统行为与验收

### 4.1 设备身份与注册

**REQ-01：注册不依赖绑定成功。** 来源 U2/F2，候选。
前提：枚举方提交有效描述，当前无匹配驱动。
行为：设备可以注册并接受管理查询；不能伪装为已可供消费者使用。
验收：无驱动注册、晚注册驱动、所有候选失败分别可观察，身份保持一致。

**REQ-02：身份存活与运行可用性分离。** 来源 U1/U2，候选。
行为：解绑不更换设备身份；保留设备引用不阻止资源退出。注销后旧引用只可
查询允许保留的信息，不能恢复注册或硬件权限。同位置再次注册是新设备。
验收：覆盖解绑后、重绑定后、注销后、同位置新设备四种情形及最终引用释放。

**REQ-03：设备事实具有明确权威来源。** 来源 U1，候选。
行为：总线归属、描述、父关系和发布来源不得由多个可独立修改的副本分别决定。
允许具有明确语义的快照与派生缓存，不以通用字符串或公开数字 ID 猜测对象同一性。
验收：不同查询入口观察同一事实；对象错配被拒绝；快照与实时查询的差别可说明。

### 4.2 驱动绑定与资源

**REQ-04：绑定是可结束、可重新建立的关系。** 来源 U2/F2，候选。
行为：成功 probe 的运行数据归本次绑定；解绑调用退出协议并释放本次资源，
设备仍注册。解绑结束后保持未绑定，不被无关驱动注册或依赖唤醒立即重新绑定。
验收：一次正常绑定、解绑、重复解绑及并发解绑，确认清理次数和最终可观察状态。

**REQ-05：显式重新探测保持对象身份。** 来源 U2，候选。
行为：已注册、未绑定设备可重新匹配；允许重新尝试此前失败的候选。
对正在 probe/解绑/注销的对象须明确拒绝或串行化；不能创建替代设备来冒充重绑定。
验收：首次失败后恢复、解绑后重探测、外域引用、注销后引用、并发重探测。
是否提供指定驱动的强制绑定不属于首阶段建议范围。

**REQ-06：失败具有明确的副作用收尾。** 来源 U1/U2/P2，候选。
行为：资源申请失败、probe 失败、延迟探测都不能遗留仍可使用的失败绑定能力。
每项获得的资源须有明确所有者及失败释放路径。无法回滚的注册不能默认为可解绑。
验收：在多次资源申请、发布、依赖等待前后注入失败；检查资源、可见发布及重试结果。
现有静态 provider 的历史限制不能自动视为满足本条，处理范围见 D2。

**REQ-07：依赖等待与恢复可判定。** 来源 F1/P2，候选。
行为：临时缺少依赖与永久失败可区分；依赖在“检查—进入等待”之间就绪不丢失唤醒。
显式保持未绑定的设备不参与自动恢复。等待结束后可诊断未满足的依赖。
验收：使用确定性同步构造依赖先到、后到、交错到达和显式解绑的组合。

### 4.3 发布与退出

**REQ-08：设备存在不等于某次发布仍可用。** 来源 U2/U1，候选。
行为：解绑或失败关闭的旧发布不得因新绑定成功而复活；来源不得悄悄改成新驱动。
一个设备允许多项发布，撤销单项发布不等于注销设备。
验收：保留旧消费者句柄跨越失败、解绑、重绑定，检查来源信息和新操作准入。

**REQ-09：新操作与在途操作有明确退出规则。** 来源现有 class 契约/P2，候选。
行为：退出关闭新操作准入；已取得许可的操作可按契约完成或取消，其依赖资源
在安全结束之前不能释放。元数据引用和操作许可不可互相代替。
验收：使用屏障控制许可获取和撤销交错，检查资源释放次数及先后关系，不靠定时等待。

**REQ-10：注销结束注册关系。** 来源 U2/F2，候选。
行为：注销先阻止新挂接和新绑定，再按已定义依赖顺序退出；完成后不能重探测。
有未退出依赖时不能先释放其依赖的父资源；中途拒绝/重试必须具有明确状态。
验收：未绑定、已绑定、正在 probe、级联受阻和重复注销，分别检查结果及资源状态。

### 4.4 拓扑、宿主与迁移

**REQ-11：拓扑关联不冒充资源所有权。** 来源 U1/A1，候选。
行为：所属总线、物理父关系、由驱动创建的下游对象、消费者依赖须能说明各自责任。
不能仅因对象处于父节点下面，就无条件认定它由当前绑定创建。
首阶段不能安全处理的解绑应在副作用开始前拒绝，明确原因，不退化为 remove+add。
验收：检查挂接与退出竞争、父/控制器不可用、下游阻止解绑；完整支持范围见 D2。

**REQ-12：宿主实现与可移植驱动隔离。** 来源 P1，硬约束的候选细化。
行为：具体驱动通过契约申请 MMIO/IRQ/DMA 等能力、发布家族能力；不能直接调用
host-kernel 实现。设备相关请求携带正确设备语义，框架全局服务不伪装成设备私有资源。
验收：检查真实适配器与驱动依赖方向；同一接口可用测试宿主验证设备归属和失败返回。

**REQ-13：迁移不产生双重设备管理。** 来源 A1/P1，候选。
行为：一台迁移设备只能由一个模型负责绑定、资源和退出；不得新旧框架重复 probe、
重复发布或重复释放。未迁移设备沿原路径工作，不要求同时重写文件系统和全部驱动。
验收：记录目标设备进入哪个模型、IRQ/资源/发布次数，同时运行未迁移设备的回归。

**REQ-14：真实设备闭环是采用模型的验收门槛。** 来源 A1，候选。
行为：至少一条真实设备路径经过枚举、真实宿主能力、probe、class 消费、
失败收尾、解绑/重绑定和最终注销；不能以 legacy class 桥接替代新 model 的绑定验证。
验收：目标设备/平台见 D1；证明资源与发布来自实际路径，列出哪些结果由 UT、
QEMU 运行或人工代码评审提供证据，不相互冒充。

### 4.5 并发、诊断与质量

**REQ-15：管理操作结果可判定。** 来源 P2/U2，候选。
行为：同设备的 probe、解绑和注销不会并发取得冲突所有权；外域/错对象、
重复请求、忙、无匹配、缺依赖和不支持操作可诊断。失败不得留下部分可用的退出状态。
验收：确定性并发交错与错误注入；验证只有合法认领方调用退出，其他请求结果明确。

**REQ-16：调用上下文与资源增长可解释。** 来源 P2，候选。
行为：管理 API 不作为硬 IRQ 入口；硬 IRQ 经规定能力通知。驱动回调和释放流程
所需的可阻塞条件必须写入契约，不能在禁止阻塞的上下文执行可阻塞清理。
多次绑定/解绑不能无界积累绑定资源、注册项或临时来源；有意保留的历史记录须说明。
验收：检查调用链和清理上下文；重复生命周期测试比较活跃资源与注册数，元数据
按持有者解释。当前无性能阈值，不虚构吞吐、延迟目标，也不把 UT 当性能测试。

## 5. 验收入口候选（待确认）

- **主要模型入口**：从公开注册、匹配、解绑/重探测、注销接口验证可观察结果，
  测试宿主用于注入资源失败与依赖到达；不把内部字段布局当验收契约。
- **消费者入口**：从 class 发布与消费者许可验证旧句柄、来源及在途操作行为。
- **真实集成入口**：使用 D1 确认的设备，通过实际枚举与宿主适配消费能力。
- 既有 UT 作为回归资产；与新需求冲突的旧断言需明确列出变化，不能机械保留。
- 代码 review 另检查职责、单一所有权与边界；测试通过不替代架构确认。

## 6. 首阶段范围建议与待决项

| 项目 | agent 推荐 | 需要确认的范围 |
|---|---|---|
| D1 真实验收载体 | aarch64 QEMU 的 VirtIO MMIO RNG，沿用 hwrng/entropy 消费链 | 首阶段先一条总线接入路径，不同时要求 PCI、多平台和所有设备家族 |
| D2 动态依赖完整度 | 首阶段完成无活动下游、无不可撤销 provider 的设备闭环；复杂拓扑/provider 解绑明确拒绝 | 是否允许这个阶段边界，还是必须首阶段完整支持控制器和可撤销 provider |
| D3 tickets 落点 | 本地一票一文件、显式 blocking edges，评审批准后再标 ready | 当前无 tracker 配置；是否采用本地文件，或配置外部 issue tracker |

D2 不豁免安全需求：不支持的操作必须提前拒绝，不能静默丢掉资源清理义务。
静态 provider 未完成可撤销设计前不列入“已支持动态生命周期”的功能清单。

首阶段建议不做：驱动模块动态装卸、强制指定驱动、PM/suspend、全量总线迁移、
完整 Linux sysfs/uevent ABI 复刻，以及没有真实用例的扩展框架。
这些是范围建议，不表示它们永远不需要，也不是用户已批准的删减。

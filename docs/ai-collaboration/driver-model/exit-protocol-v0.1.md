# 退出协议：许可、清理执行权与等待

状态：设计候选，配合 [结构 v0.2](architecture-v0.2.md) 评审；尚未实现。
依据：需求 R03—R08、Linux 上下文约束、现有 class/kfinalize/kirq 源码。
本稿收敛并发协议，不增加公共设备 ID、任务管理器或任意超时机制。

评审更新：结构设计第 12 节按前置能力成立继续设计，为当前方案。本文第 2 节
强制两级 gate、第 5 节可失败等待准备、第 10—12 节整树认领/准备结果交接均已
被替代，不作为实施要求。仅保留单项许可、明确退出责任及收尾上下文等不变量；
第 13 节的注册权与违约保底仍为候选。不能把历史机制与精简方案同时实现。

## 1. 三个完成条件不能互相冒充

| 完成条件 | 由谁证明 | 不证明什么 |
|---|---|---|
| 使用排空 | class 许可计数在关闭后归零 | 不证明设备已停止 DMA，也不证明 hook 已完成 |
| 硬件停止 | 驱动及 IRQ/transport 契约 | 不证明 class 注册项和系统投影已移除 |
| 发布收尾完成 | 单项清理执行权持有者完成 hook 后发出完成通知 | 不证明整个设备已经注销 |

model 只有在本次绑定所需收尾全部成立后才能提交未绑定。设备注销额外结束
注册及拓扑关联；所有元数据引用消失从来不是这三项条件中的任何一项。

## 2. 许可取得与关闭

单项发布和共享作用域各有一个受短锁保护的 gate/count。状态为 Open、Closed；
Closed 不会回到 Open。新一次绑定使用新的作用域和发布对象。

取得操作许可的逻辑顺序：

1. 在单项锁内确认 Open，取得该项清理义务的强引用，增加单项使用数。
2. 释放单项锁，在作用域锁内确认 Open 并增加组内使用数。
3. 第二步失败则撤销第一步所得许可，不进入 runtime；全部成功才返回 InUse。

两级锁不嵌套。计数增加与 gate 检查在同一锁内完成；不采用先查询 online、
退出线程看到零后再无条件增加计数的协议。计数溢出必须在增加前拒绝，不回绕。

退出将对应 gate 改为 Closed；计数为零时建立排空终态，非零时等待最后的
归还建立终态。归还只降低自己成功取得的许可，不补发或转移权限。
通知在锁外执行。只要进入 runtime，组和单项各恰好有一个许可覆盖该操作。

这里的许可只保护受其约束的数据面调用。IRQ、DMA、独立 work 的访问必须由
驱动另行停止/同步，不能把它们隐含计入 class 的计数。

## 3. 唯一清理执行权

单项发布拥有一份清理记录，状态为：

```text
Pending → Running → Done
```

这里 Pending 表示 hook 尚未执行，并非 publication 尚未发布。执行前还必须
满足已关闭、已排空、移除通知已结束，以及该 hook 所需的驱动收尾前提。
取走资源并释放必须晚于所有依赖它的 hook。停止硬件不等于已经释放硬件资源；
不能先释放 runtime 所需资源，再把仍接收 runtime 引用的 hook 当成纯元数据操作。

- 正常任务退出和 worker fallback 都经过同一个短锁内的 Pending → Running。
- 只有成功领取者取走 hook，解锁后执行；其他调用者只观察或等待结果。
- 执行完毕再提交 Done 并通知，不能在 hook 执行前把“已领取”当成“已完成”。
- 重复 withdraw 不重复删除、发送移除通知或执行 hook。
- 若 hook 按契约不能失败，不将 panic 当成可恢复成功；若后续需要可恢复错误，
  需要独立说明其失败状态与可见后果，不能沿用 Done 表示未完成。

class 内的清理记录负责 hook，不负责替驱动执行 stop。fallback 也不能修复
驱动在仍有 DMA 时丢失资源所有权的错误。

## 4. 引用关系与 DeferredArc 的使用范围

候选关系为：

```text
Registration ──强持有──> 清理义务 DeferredArc
InUse        ──强持有──> 同一清理义务 DeferredArc
Publication  ──弱关联──> 清理义务
清理义务     ──强持有──> 清理记录/必要 runtime/来源
Publication  ──强持有──> 运行外壳及查询状态
```

清理记录和运行外壳不能反过来强持有清理义务。Registration 关闭单项 gate，
移出 class 表并完成移除通知之后才释放其义务引用；通知未结束时不能让
fallback 提前执行 hook。获得 InUse 时在同一 gate 协议下升级弱关联。
因此合法操作持有义务，消费者裸引用不持有义务，失效引用不会阻止收尾。

显式路径可以在持有义务时领取并完成 hook；随后义务的延迟析构观察 Done
成为无操作。若未显式领取，最后义务引用释放才将 Pending 交给 worker。
不能使用 DeferredArc::strong_count 判断业务排空；它只实现析构责任转交。
runtime 内的活动资源通过显式 stop 移出并释放，不能依赖裸 Publication 的
最后引用；残留外壳的析构需满足其可能发生的上下文。

注册权管理与使用许可的析构上下文不相同：publish、withdraw、Registration Drop
属于可睡眠任务上下文的管理操作，因其需要操作注册表和调用通知。这里不承诺
Registration 可以在 hardirq 任意丢弃。InUse Drop 仅归还许可、通知及转交已准备
清理义务，不内联可能睡眠的 hook；合法上下文仍受具体许可/宿主契约限制，不
笼统扩展到 NMI。裸消费者句柄的最终析构要求失效外壳无睡眠清理责任。

因此“不阻塞的 Drop 保底”只可指不等待在途使用的 Registration 撤销，不意味着
整个 Drop 任意上下文安全或通知绝不阻塞。需要同步退出时使用显式等待路径。

对 class 中需要睡眠的最终析构，这一关系提供现有 kfinalize 的适配位置；
不把所有 Arc 替换成 DeferredArc。构造需正常 provider 就绪的可睡眠任务上下文。
启动早期若 provider 未就绪，必须调整接入时序或使用经审计的已有启动接入，
不能默认降级成任意上下文执行析构。

## 5. 等待协议：准备先于不可逆动作

每次退出的一次性完成条件都不重置给下一次绑定复用。宿主等待凭证包含当前
任务的 PreparedTaskWait 及已经成功登记的完成通知，不仅是一个 Waker。

1. 在退出尚未不可逆时校验可睡眠上下文，准备等待资源。
2. 登记对应完成通知并复查完成状态，若已完成直接返回。
3. 执行关闭/撤销后，只能使用已准备资源等待；不得再依赖临时分配。
4. 虚假唤醒重新检查终态，登记仍保留；终态完成才允许通知拆除登记。

一次性完成只在 Closed 且 count 为零时发信号，不能像普通状态更新那样
多次 wake 后消耗登记、重新申请。已终态的后到观察者直接读取完成结果。
通知不能在持 class/model 状态锁时执行任意消费者代码。

PreparedTaskWait 本身不会在 park 中登记等待，也不会自动处理这些条件，
所以 os-api 不能用它的名字掩盖完成登记义务。

## 6. 回调重入：遵循 Linux 前置条件，不造检测系统

本地 Linux `drivers/base/dd.c:1388` 明确指出，在 remove 内递归解绑同一设备
会死锁。Linux 一致的要求不等于框架必须自动发现任意等待依赖环。

因此修正早期“自动检测并拒绝所有重入”的过度承诺：

- probe/remove/hook 不得同步等待由当前调用栈阻止完成的生命周期操作。
- 操作中不得持有在途 IRQ/消费者必须取得的锁等待其结束。
- 不持 model/class 表锁调用驱动、通知订阅者或执行可能睡眠的 hook。
- 合法的跨任务同设备操作串行化，完成后重新校验状态；对明显无效状态返回
  相应错误。不同设备操作不被全局回调锁串行化。
- 不新增全局 task ID、回调栈注册表或通用死锁检测器。调试断言可辅助已知路径，
  但不作为安全协议成立的唯一条件。

即便当前没有生产用户直接重入，订阅通知和子对象退出也要按这个约束检查。
只有明确无需等待当前操作完成的子操作才允许从回调中同步执行。

## 7. 交错证明与测试表

| 交错 | 必须得到的结果 | 关键依据 |
|---|---|---|
| 单项许可成功，组关闭，再申请组许可 | 失败并归还单项许可，runtime 不运行 | 进入 runtime 需两级许可 |
| 两级许可成功，随后关闭 | 该操作可安全完成或被驱动取消，退出等待它 | 关闭前已计入两个 count |
| 单项关闭与弱义务升级竞争 | 关闭先发生则拒绝；升级成功则强持有直到归还 | 同一单项 gate 锁 |
| 最后 InUse 归还与退出等待登记竞争 | 不丢失完成，也不重新分配才能继续 | 登记后复查、单调终态 |
| 显式收尾与 fallback 同时领取 | hook 恰好一次，另一方观察 Running/Done | 唯一 Pending → Running |
| 旧 Publication 永久保留 | 不恢复许可，不拖住已关闭绑定的硬件资源 | 裸句柄不保有清理义务，资源显式移出 |
| 阻塞 RNG read 与解绑 | 读者被停止条件唤醒并退出，不等新的熵 IRQ | stop/wake 早于等待排空 |
| probe 返回成功与注销认领竞争 | 成功 Data 要么提交绑定，要么被承接并执行退出 | 不能因提交资格失效直接 drop 活动 Data |
| 一个实例退出而另一个继续读 | 第二实例发布、IRQ action 和资源不受影响 | 每实例作用域及共享 IRQ token 隔离 |

这些是设计推演及后续 UT 目标，不是已运行的证明。特别要验证通知的重入与
最终析构上下文，不能只检查最后资源计数等于零。

## 8. reset 故障与真实依赖边界

不在通用 model 内引入任意 reset 超时或“超时后强制释放”。本地 Linux 的
VirtIO PCI reset 写入状态后等待设备归零，再同步向量；MMIO reset 是 transport
自身定义的不同流程。不能凭同名 reset 假定所有传输都具备同一确认机制。

本阶段正常退出需证明所选传输停止设备访问，再取消未完成请求和释放映射。
如果停机未能得到证明，不能提交成功退出或允许重新绑定复用旧资源；维持退出
状态和资源所有权，不用物理资源泄漏伪装成功。故障可观测方式随 transport
接口设计明确，未获依据前不承诺有界退出时间或自动恢复。

新的实质依赖核对：kvirtiodrivers Hal 是静态关联函数，当前 VirtIoHalImpl
使用全局 provider，不能直接携带每实例 DmaInfo。新模型的设备 DMA 约束不能
通过 TLS、临时“当前设备”或复制全局默认值来冒充支持，否则多实例并发会错配。
库适配设计必须解决 queue/request 的设备 DMA 上下文或证明所选后端的适用边界；
未完成前不把“新 os-api 已接入”列为真实链路验收完成。

## 9. 本轮收敛结果

- 不再要求通用重入检测，使用 Linux 一致的明确调用前置条件及内部锁序。
- 许可准入、资源停止、hook 完成分别有责任与可观察条件。
- DeferredArc 只承担预准备的清理义务转交，显式退出与 fallback 共享执行权。
- 不新增通用 executor，不虚构 reset 超时，不允许以当前全局 HAL 隐藏设备 DMA 约束。

结构与并发方案可提交 review；第 10、11 节补充退出准备交接及下游所有权候选。
等待完成 Interface、VirtIO shutdown/设备 DMA 上下文和 kirq 同步释放仍需按
集成契约实施验证，不能把本文的推演作为已完成的代码验证。

## 10. 准备结果如何交给退出执行

本节是候选契约，不声称 Linux 具有同名的两阶段 remove 回调。两阶段的原因
是当前宿主等待登记可失败；不能在撤销之后才发现没有能力等待资源停止。

### 职责和交接

- model 负责生命周期操作的独占认领、绑定身份核对、框架等待与最终状态提交。
- DriverOps 增加准备退出的职责：借用本次 Data，返回拥有等待凭证的准备结果；
  remove 消费该结果并访问同一份 Data。暂称 RemovePreparation，其类型交接
  见第 12 节；准备结果不借用 Data，不复制其资源所有权。
- 准备结果仅由执行任务的局部退出计划拥有，不要求 Send/Sync，不存入设备共享状态。
  类型擦除层在同一任务中配对准备与执行，不把任务绑定的等待凭证跨任务投递。
- 无异步退出义务的驱动使用空结果；不能要求其构造虚假的 IRQ 或 class 计划。
- os-api 提供已登记的等待凭证；class 和 IRQ adapter 分别绑定具体发布项和
  action 的完成条件，不用设备级“全部完成”替代各自的资源同步。

准备仅登记通知、保留稳定对象和验证上下文，不撤销发布、不停止硬件、不等待
尚未停止的业务请求。失败时 Drop 准备结果只取消等待登记，不运行 remove。
成功交接后 remove 不能再为必需的退出等待进行可失败分配；它仍可阻塞。
准备成功不保证硬件一定停机，停机未确认不得释放资源或提交 Unbound。

### 稳定性：认领管理操作，不提前关闭数据面

单有“快照后检查一次版本”不够：检查与关闭之间仍可能新增发布或下游。
采用短锁内认领、锁外准备的协议，管理认领与消费者 gate 是不同概念：

1. 在锁外预留计划存储，读取稳定引用与所属关系版本；短锁内复核并认领这次
   退出涉及的绑定及注册管理权。关系变化则重试，不在持锁区分配。
2. 准备期间，已认领集合不允许提交新的下游注册或改变所属关系，也不允许
   另一生命周期操作取得这些 Data。相关管理请求串行化，或取得明确的可重试
   结果；失败请求不能留下半注册对象。普通设备操作、IRQ、完成通知仍可运行。
3. 若存在正在 probe/remove 的冲突对象，不持有部分集合的认领等待它；释放
   本次临时认领，锁外等待已有操作结束后重新收集。不得父认领等子、子又等父。
4. 在认领保护下准备框架及各驱动所需凭证；任一准备失败，取消所有准备结果、
   释放管理认领并通知等待者。没有发布被撤销，没有数据面 gate 被关闭。
5. 全部准备成功才进入不可逆执行，认领持续到提交结束。准备取消可以放开管理
   请求，但已经关闭的数据面 gate 永不重开；二者不能共用一个 online 布尔值。

“准备失败无副作用”准确指没有不可逆的设备/发布变化；管理请求可能短暂等待，
并非准备过程对所有并发调用都完全不可见。等待认领的调用也不得持有退出所需锁。

驱动在绑定期间动态改变自己持有的 publication/IRQ 集合时，必须使用同一个
管理串行化约定，或在自己的准备回调中取得集合变更的保留权，并持有至执行结束。
不能仅复制一个列表后声称安全；不新增覆盖所有硬件活动的全局计数。

probe 的部分初始化守卫在启动异步活动、向消费者发布之前，就建立回滚必需的
完成条件与清理能力。失败回滚不能依赖“之后还可成功调用 prepare_remove”；
正常退出和回滚复用底层停机动作，不要求框架对失败 probe 调用成功绑定的 remove。

## 11. 下游注册权与控制器服务

### 所有权不是 parent

DeviceRef 保有身份；注册权承担注销责任；parent 描述拓扑。三个概念不能互换。
model 的注册记录是注册归属的权威来源，注册权对象只是对此记录的撤销权限，
不另存一份可变的子设备表。设备身份引用不反向强持有控制器的绑定 Data。

主机集成层持有根注册权。控制器的一次绑定持有自己创建的下游总线/设备注册权；
具体总线模块规定自己的枚举和退出顺序。受绑定管理的注册入口必须带该次绑定的
创建权限，不能只传 parent 后悄悄变成永久注册；显式的启动注册入口归主机集成。
注册记录只关联创建者，不复制其名称或描述，也不增加公共数值 ID。

下游所有权只允许附着于仍有效的创建者，禁止成环和运行中任意换主；不能从
静态 parent 遍历推导所有权。静态固件子设备不会仅因父驱动解绑被自动注销；
若其注册本来属于控制器管理的总线，则即使来源是固件，也随该总线退出。
描述来源是固件还是动态探测，本身不决定注册所有权。

### 创建与退出的交错

注册提交与管理认领在同一注册状态协议中串行化：

- 注册先提交：关系版本变化；退出必须把该对象纳入准备集合，不能漏掉。
- 准备认领先发生：注册尚不能提交，调用者仍负责未注册对象；取消准备后可重试。
- 不可逆退出已开始：旧创建权限失效，迟到枚举结果必须回滚，不能挂到下一次绑定。

阻止提交不等于枚举工作已经停止。具体总线仍要停止枚举源并同步正在执行的
枚举工作，然后才能释放其访问的控制器资源。同步过程不得等待一个持有管理锁、
又在等待自己退出的注册调用；注册失败路径应允许枚举者完成自身回滚。

### 下游先退出，控制器后停机

这里修正“先统一关闭父设备所有能力”的过强顺序。下游 remove 可能需要父控制器
执行最后一次总线事务，所以关闭下游创建权限不能同时关闭控制器全部服务：

1. 对拥有关系覆盖的退出集合完成第 10 节准备，进入不可逆退出，拒绝新增下游。
2. 总线模块停止并同步枚举源，按本总线顺序注销拥有的下游。
3. 子设备按各自协议关闭准入、退出驱动并结束注册；父控制器服务和相关资源保持
   可用。父管理操作已被认领，但不能持有子设备正常事务所需的锁等待子设备。
4. 下游全部退出后，才关闭父绑定自身的数据面作用域，执行父设备停机和资源释放。
5. 最终提交父绑定退出；若只是解绑，父设备本身的注册仍然保留。

因此下游退出期间，父设备已有消费者也可能仍能调用服务；解绑尚未完成，不承诺
发起解绑瞬间所有层级同时不可用。这里不新增绕过关闭 gate 的“特权访问句柄”。
如果某总线另有服务关闭顺序，应由总线契约证明，而非修改通用 parent 语义。

注册权的同步注销必须显式执行。Drop 不能隐式遍历整棵树并执行可睡眠 remove；
漏掉显式注销是生命周期违约，不能通过直接释放尚活跃 Data 来掩盖。正式接口
采用第 13 节的诊断及保留安全所有权方案，不宣称 RAII 自动完成硬件停机。

### 本地 Linux 依据与边界

- `drivers/pci/remove.c` 的 pci_stop_bus_device 先递归 subordinate 再停止当前设备；
  pci_stop_root_bus 先停止总线设备再解绑 host bridge，并由 PCI 的 rescan/remove
  串行化约束保护管理操作。这不是通用 driver core 按任意 parent 自动遍历。
- `drivers/i2c/i2c-core-base.c` 的 i2c_del_adapter 先撤掉适配器的可发现入口，再
  注销 clients，随后拆除 host notify IRQ；clients 的普通/dummy 两遍顺序说明
  退出次序包含总线知识，不能硬编码成 model 通用的一次列表遍历。

以上核对本地 Linux 源码，只支持责任与先后关系；本设计的准备凭证与注册权
是针对本仓库的适配，不声称是 Linux 原有类型。本阶段以模型 UT 覆盖拥有关系，
真实集成仍是 hwrng，不因此扩展成实现 PCI/I2C 新子系统。

### 必须验证的交错

| 场景 | 必须结果 |
|---|---|
| 准备期间某个子设备准备失败 | 全部临时准备取消，原发布及硬件继续工作 |
| 新子设备提交与父退出收集竞争 | 纳入计划或未注册，不存在退出集合外的成功挂接 |
| 子操作先认领，父退出随后到来 | 父释放临时认领后等待，不持父管理权阻塞子完成 |
| 子 remove 调用父控制器事务 | 父服务仍有效，未持其事务锁同步等待子退出 |
| 枚举结果在父关闭后迟到 | 原调用负责回滚，不挂入新绑定 |
| 静态 parent 相同、注册所有者不同 | 不因父绑定退出误删另一所有者的注册 |
| 任意旧 DeviceRef/Publication 长期保留 | 不拖住已显式退出的硬件资源，不恢复创建/操作权限 |

这些是候选契约与测试要求，不是已经运行的验证。不会以文档完整替代接口原型
的类型检查、错误注入及实际 hwrng 解绑/重绑测试。

## 12. 准备结果的类型交接

### 对驱动保持具体类型，对 model 只隐藏内部差异

选择 DriverOps 的关联类型 RemovePreparation，而不是给 Data 加 Option 字段，
也不把等待凭证加入 Send + Sync 的 DataBox。驱动声明自己的准备结果类型，
prepare_remove 返回该类型，remove 按值消费它；简单驱动明确使用 ()。
关联类型要求 'static，但不要求 Send/Sync：'static 表示不借用本次 Data 或
栈上的 DeviceAccess，不表示结果永久存在，也不表示可跨任务使用。

本地 PreparedTaskWait 持有 KtaskRef、Arc<KWaker> 和任务绑定标记，而非借用
栈上的任务对象，因此拥有型、非 Send 的等待凭证与此约束相容。os-api 的
已登记等待句柄也采用拥有完成对象/登记的形状；不向驱动暴露 ktask 类型。
不是所有 MutexGuard 都适合放入准备结果；集合稳定性优先由 model 管理认领
保证，驱动自管集合需要拥有型的变更保留权，不能偷偷延长借用生命周期。

现有 AnyDriver 已将具体 Data 擦除成 Box<dyn Any + Send + Sync>。新的私有
适配层可另外返回 Box<dyn Any> 包装准备结果，不加 Send/Sync；这次装箱和计划
容器的分配全部发生在不可逆退出前，沿用仓库真实的分配失败策略，不承诺
Box::new 能返回可恢复的 OOM。可恢复的准备错误与内核全局 OOM 策略分开描述。

model 的任务局部计划同时持有本次绑定的稳定引用、创建它的驱动适配器和准备
结果。结果不能由调用者从外部任意指定，也没有按公共 ID 查询/提交准备结果的
接口。执行时只向原适配器交付原绑定的 Data 和结果；适配器恢复具体类型后
调用驱动。类型匹配不是实例匹配，同一驱动的两个设备仍须由绑定引用配对。
原绑定已被独占认领，不能在准备与执行之间换成新一代绑定。

任务局部计划自身也禁止 Send/Sync，即使某个驱动的准备结果恰好是 ()；准备、
执行及取消均在原任务进行。不使用 unsafe Send 包装，不把结果投递给通用 worker，
也不增加任务 ID 注册表。具体等待实现仍校验可睡眠上下文。

### 取消与完成

- 准备阶段取消：先销毁各项准备结果，取消登记/变更保留权，再释放管理认领。
  已有 Data 仍属于原绑定；不能将准备取消等同于驱动退出。
- 执行阶段：消费准备结果不等于消费 Data。活动 Data 由绑定保有，退出调用获得
  独占访问；只有正常完成约定的收尾后，model 才移除并释放 Data。
- 同步 remove 没有“调用者不想等了就丢弃任务”的取消语义。不引入可被随意丢弃的
  退出 Future。若以后支持异步取消，必须另行设计已开始退出的责任承接。
- 硬件停止未确认时不能正常返回并提交成功，也不能因销毁准备结果释放活动资源。
  本阶段不承诺有界停机时间或故障后自动恢复；保留第 8 节的安全底线。

这里选择沿用私有类型擦除，而非公开 dyn Any 或加入通用事务框架。实现验收必须
包含非 Send 准备结果、两个相同驱动实例不混配、取消无撤销、关闭后无等待分配。
尚未以真实 os-api 做编译验证，不能把本节静态核对称为编译或运行测试通过。

## 13. 遗漏显式注销的安全保底

本节只定义 model 的设备/总线注册权，不改变 class::Registration 已定义的
任务上下文撤销行为。二者管理的对象不同，不能因为都叫注册权而共用 Drop 策略。

### 注册记录持有活动所有权，凭证持有管理权限

注册成功后，由 model 的记录持有设备、当前绑定及必要的宿主资源所有权；
注册权对象不是这些活动资源的唯一持有者。显式 unregister 借助注册权发起，
准备失败时注册权仍可用于重试，成功才标记已注销。消费者的 DeviceRef 没有
注销权限，也不因为最后一个消费者离开就移除设备。

若尚未注销的注册权被丢弃，Drop 只在已有记录中标记管理凭证丢失，不能分配、
调用驱动、等待 IRQ、遍历孩子或触发可睡眠 hook。该标记供任务上下文的诊断路径
报告；它不是一次成功注销，也不会立即撤销仍可能被下游使用的控制器服务。
记录继续保留活动所有权，不能直接释放 MMIO、DMA 或 IRQ guard。

父绑定正常退出仍可按权威拥有关系收集这条记录，不依赖子注册权对象还在用户
手里。已认领的内部退出计划代表模型管理权，可完成其收尾，但不是向消费者
重新发一个可复制的注销凭证。根注册由主机集成层的显式关闭流程回收。
凭证丢失诊断不允许把该对象从拥有集合中跳过，更不能让父资源先被释放。

### 失败关闭，而不是伪装成自动清理

model 的正常 shutdown 必须显式注销全部记录，失败时保留 model 以供诊断或重试。
活动记录存在时最后一个 model 所有者被丢弃，也是生命周期违约。最终 Drop 的
安全保底只能保留整份活动状态及其依赖，不能让容器析构顺便释放硬件资源。
实现可对仍活动的状态使用明确的保留/泄漏路径，退出已完成的空状态则正常释放；
不能只保留 Data 却提前释放它依赖的宿主、总线或控制器对象。

这是有意选择“违约时可能保留资源，而不是产生 DMA/IRQ use-after-free”，不是
无泄漏保证，不是正常退出策略，也不是硬件停机失败时返回成功的理由。必须提供
可检查的违约状态和诊断，正常路径及故障注入测试不得以这种保底冒充通过。
不把未知睡眠退出塞进 kfinalize 的共享串行 worker，避免等待同一执行器造成死锁。

### 验收条件

| 情况 | 要求 |
|---|---|
| unregister 准备失败 | 注册仍在，调用方保有重试权限，Data 未析构 |
| 正常显式注销后丢弃凭证 | 无重复通知/回调/资源释放 |
| 活动凭证被丢弃 | 可诊断，资源仍在，不在 Drop 内执行驱动代码 |
| 子凭证丢失后父绑定退出 | 仍收集子记录；子退出完成前父资源不释放 |
| 最后 model 所有者错误丢弃 | 不析构活动硬件状态；明确记录保底资源保留，不能算成功退出 |

第 10—13 节给出集中评审候选，不授权实现新总线子系统，也不声称已经获整体
设计批准。后续实现需验证这些接口和失败路径，而非再由实现者自行猜测保底行为。

# Ticket 01B/03：单项发布撤销的局部设计

后续分层修订见 [hwrng 生命周期设计](hwrng-lifecycle-design.md)：以下把同步
排空统一归于通用 class 的候选方向已撤回，改为由 hwrng 定义其使用生命周期。
DeferredArc 仅在析构上下文确有需要时选用，不是必需依赖。相关接口尚未实现。

状态：设计草案，尚未编码。Ticket 02 验收通过，改动仍在独立 worktree 等待提交。
本稿承接 architecture-v0.2 第 6、13 节，不恢复整树准备、组级准入或通用退出事务。
接口名称用于讨论，不是已经批准的公开 Rust 类型。

## 已确认：退出与析构分开

管理者负责退出，引用负责保活，DeferredArc 负责最终析构。
remove 保持无错误返回契约：驱动必须在返回前完成退出，不增加通用失败绑定
状态、退出重试事务或后台补做 remove。硬件异常由具体驱动/总线处理，
不意味着可以释放仍被 DMA 使用的内存。
成功绑定未完成退出就销毁管理凭证属于生命周期 bug，不是受支持路径。
用契约、诊断和测试发现错误；具体诊断方式待定，不默认等于 panic。
probe 失败是合法路径，构造回滚必须完成已启动硬件和已发布能力的收尾，
不能依赖框架对失败 probe 补调 remove。

核对 ktask：notify_exit 发布退出状态并通知 joiner，调度器随后切出；
finish_task_switch 在新栈上清理退出参与状态并释放旧 current 引用。
外部 KtaskRef 可以继续存在，最后引用释放才触发 DeferredArc 析构。
join 不保证对象析构，甚至不能替代调度器的切换后收尾；丢弃一个 KtaskRef
也不会主动退出任务，因为调度器仍持有活动任务。

因此 class 的同步撤销应等待业务退出及 hook 完成，不等待整个 T 的析构。
旧消费者可以保留已停止的 runtime，不强制另拆身份外壳，也不要求通用
PayloadSlot、UnsafeCell 或 DeferredArc::unwrap。需要延迟析构的对象仍可
通过 DeferredArc 保护，但它不是硬件停机的执行器。

本轮范围包含安全解绑和重新绑定。现有 virtio-rng 尚无 teardown 是待补齐的
实现缺口，不是缩小验收范围的依据。完整责任链是：

1. model 串行化该设备管理操作，保留本次绑定及其 Data，调用驱动退出流程。
2. 驱动通过 class 关闭发布准入，停止新请求并使阻塞读者能够结束。
3. class 排空已准入操作并完成撤销 hook；驱动按硬件协议停止 DMA、同步
   注销 IRQ、回收请求和队列。硬件仍用于完成已有请求时，不能机械地先禁 IRQ。
4. 只有本次绑定已不再访问硬件且应解除的资源都已解除，model 才完成解绑，
   允许对仍注册的设备重新 probe。remove 必须履行这一责任，model 不提供
   通用的停机失败重试协议，也不能重新开放旧发布。
5. 新绑定创建新 runtime 和发布。旧句柄永远失效；旧对象的最终内存释放可延后。

驱动应把 IRQ、DMA、队列的显式解除封装在自己的停机操作内，通过既有锁和
资源 guard 管理；不能让通用 class 猜测 T 内部布局。必要时在具体驱动内保存
可取走的资源状态，但不把这个局部需要推广成所有发布必须遵守的 payload 容器。
Registration 必须显式完成撤销；未退出就 Drop 属于 bug，不设计异步撤销
兜底。实现时必须迁移现有自动撤销 Drop 的调用点和合法构造回滚，不能仅删除
旧 Drop。诊断方式须符合仓库规则，不宣称 bug 路径天然内存安全。
本次只调整设计，不修改生产代码。

验收应区分“解绑必须完成的资源解除”和“对象最终析构”：保留旧句柄完成
解绑/重绑后，旧操作失败、旧 IRQ 已解除、旧 DMA 已停止，且新绑定可正常运行；
释放旧句柄不能再注销新绑定的 IRQ 或改变新绑定状态。

## 1. 模块职责

| Module | 拥有的事实与责任 | 不拥有 |
|---|---|---|
| os-api 等待契约 | 单次完成的通知、等待、上下文与失败语义 | 设备、发布表、使用计数、退出顺序 |
| X-Kernel Adapter | 用 kcompletion/ktask 实现契约 | class hook、驱动停机策略 |
| 测试 Adapter | 按相同契约控制通知/等待交错 | 通过假返回成功跳过尚未完成的等待 |
| class 单项发布 | 注册权、准入、许可计数、撤销通知、hook 顺序 | DMA 是否停止、IRQ 是否同步、设备请求取消 |
| 驱动/子系统 | 使阻塞操作可退出，停止硬件，管理自身资源 | 宿主调度器对象和等待节点 |
| kfinalize | 已准备的最终析构执行环境 | 正常解绑协议、清理结果或设备状态 |

等待契约先放在 `drivers/base/os-api` 的独立 mod，不为一个小接口再拆 crate。
宿主 Adapter 放在 X-Kernel 层，class 不依赖 ktask/kirq/kwork。构造能力由宿主
注入，不在可移植 class 中寻找全局调度器，也不把该能力塞进 PublicationSource。

## 2. 01B 最小等待契约

建议只提供“单次、永久完成”的能力，不搬出内核 Completion 的所有操作：

- 构造：发布可见之前准备对象；初始化失败返回错误，不安装半成品 publication。
- 检查等待上下文：不睡眠、不改变完成状态；供管理操作在关闭前拒绝非法调用。
- `wait`：验证当前上下文，等待永久完成；完成早于等待同样成功。
- `complete_all`：发布完成并唤醒所有等待者，可从允许的 IRQ 上下文通知。

不提供计数令牌、reset、取消、超时、异步 Future、公开等待节点或可转移任务凭证。
对象可在控制路径分配；准备完成后的通知、登记和等待不临时分配资源。
wait 错误只表示没有证明完成，不授权释放资源；成功返回具有完成前写入的可见性。
检查上下文不是永久许可证；调用方在回调/锁作用域后仍须满足 wait 的前置条件。

宿主用私有 kcompletion::Completion 保存永久完成态，用
ktask::completion::wait_for_completion 执行同步等待；可移植侧只持契约对象。
测试 Adapter 和宿主 Adapter 都验收早完成、多个等待者、虚假唤醒、非法上下文、
通知/登记竞争和数据可见性。不能拿本机测试通过推断任意外部 Adapter 合规。

本阶段一个 publication 对应一次生命周期；重绑创建新对象，不复用旧完成态。
暂不增加“hook 完成”第二个等待对象：正常撤销由唯一 Registration 管理者执行，
它完成 hook 后直接返回。若后续确认需要多个独立撤销等待者，再说明新增需求。

## 3. 03 所有权与准入方向

Registration 独占撤销管理权；Publication 是可克隆消费者句柄；InUse 保护
已准入的操作。共享引用可以保留已经停止的 runtime，不强制拆出身份外壳或
独立清理义务。资源解除由驱动的显式停机负责，整个对象析构可以延后。
来源只读，不使用 source.is_online 代替发布自身的准入决定。

准入 gate 和许可计数作为同一组不变量序列化：锁内判断可用、
增加计数；关闭在同一锁下改变 gate。该短临界区不能覆盖消费者操作或外部回调。
若许可允许在 hardirq 归还，保护它的锁也必须满足 IRQ 上下文，而不是继续依赖
仅禁止抢占的锁。先采用可证明的短临界区，不沿用多个 SeqCst 原子拼接复杂协议。

观察型 is_available 不是许可；不得根据 strong_count 快照决定可清理。
关闭后新 acquire 失败；已有 InUse 仍能访问 runtime，直到归还。

## 4. 显式退出的次序

1. 管理者验证上下文和自身退出前提，不持有消费者退出所需的锁。
2. 关闭单项 gate，移出 class 表；锁外完成撤销通知。
3. 驱动/子系统保证已有阻塞操作能退出。需要时先置停止状态/唤醒，再进入等待；
   class 不自行发明取消设备请求的算法。
4. 等待许可归零；最后许可只更新状态和通知，不内联运行 hook。
5. 管理者执行 unpublish hook，完成 runtime 的资源所有权收尾，然后返回。

分步关闭与完成撤销共用同一状态；候选为唯一注册权上的可变借用操作，而非
创建额外“退出事务”类型。管理入口必须满足等待上下文前提；非法等待不能
被当作已经完成，也不据此引入驱动解绑重试事务。关闭后不能重新开放旧发布。

hook 必须在撤销通知结束后执行，且执行一次。发布 hook 失败时仍须撤回其部分
副作用；当前 ClassHooks 契约要求调用 unpublish，不能在改造中误删此回滚。
普通来源查询不得成为绕过许可取得 runtime 的通道。

## 5. Drop 与延迟析构

不通过 Registration Drop、最后一个消费者或 finalizer 自动补做退出。
正常路径显式关闭、排空、执行 hook；未完成便丢弃注册权属于生命周期 bug。
InUse 最后释放只进行计数和必要通知，不内联可能睡眠的 hook。
需要延迟析构的对象使用 DeferredArc，但不要求从中取出整个 payload；
撤回通用 PayloadSlot/UnsafeCell 及正常/兜底共享清理执行权的候选方案。
最终析构不得等待共享串行 executor 上的其他 finalizer。

## 6. Linux 对照与适用范围

本地 `drivers/char/hw_random/core.c`：cleanup_rng 将清理排入 workqueue，
cleanup_rng_work 调用 cleanup 后发出 cleanup_done；hwrng_unregister 在释放
rng_mutex 后等待它。`virtio-rng.c::remove_common` 先置 removed 并唤醒读者，
再注销 hwrng，之后 reset/del_vqs。

这支持显式完成边界、锁外等待和先让读者退出的次序；不证明通用 class 应把
所有清理交给我们的共享串行 finalizer。Linux 的 workqueue 策略不能不加核对地
等同于 kfinalize 的执行约束。
本地 platform/virtio remove 返回 void；driver core 在 remove 后继续解绑和
释放 devres。virtio_dev_remove 检查 reset 状态并告警，没有通用退出重试事务。

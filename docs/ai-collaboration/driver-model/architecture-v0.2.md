# 驱动框架结构设计 v0.2

状态：当前设计候选，尚未批准实施。需求基线为 requirements-v0.2（内容不变）。
用户已允许重设计现有 mod/crate 命名和划分，不以现有接口或目录为保留理由。
本文替代早期职责草案作为结构评审入口；生命周期事实调查仍见
[生命周期设计](lifecycle-design-v0.1.md)。本文尚不宣称全部实现前提已经闭合。

2026-10-24 用户确认以 Linux 驱动模型的职责为目标，而非只参考局部实现。
当前结构以第 1 节及 hwrng-lifecycle-design.md 的最新分层为准；后文历史
Class<T>/PublicationScope/通用排空候选不得覆盖这项确认。其余生命周期按
第 12 节的收口方向：按真实接入契约第 11 节的前置能力已具备继续设计，
取消通用整树准备及强制共享发布作用域。第 9—11 节保留审查演进与撤回依据，
不是对旧候选机制的重复批准。本文仍为设计候选，未改实现。

## 1. 结构结论

不预先承诺保留 model/class/os-api 三个 crate 的现有划分。先对齐 Linux
职责，再按真实所有权和依赖决定 mod/crate，不以现有类型或目录为保留理由。

| Linux 概念 | 目标职责 | 不混入的职责 |
|---|---|---|
| device | 设备身份、父关系、注册与对象生命周期、bus/class/driver 关联 | 子系统业务操作计数 |
| bus_type | 总线类型的匹配及 probe/remove 接入 | 不等同于具体控制器/总线实例 |
| device_driver | 某总线上的驱动、匹配信息及 probe/remove | 设备对象的最终内存寿命 |
| class | 对 device 的功能分类、属性和对外呈现 | 任意 T 的能力注册和同步业务排空 |
| hwrng 子系统 | RNG provider 注册、选择/消费及注销同步 | 通用设备匹配和硬件专属 reset |

本地依据：include/linux/device.h、device/bus.h、device/driver.h、device/class.h、
hw_random.h 及 drivers/char/hw_random/core.c。class 遍历的是 device；hwrng
独立维护 provider 列表，公共入口使用 misc_register。两者不是同一个注册模型。

| crate | 一句话定义 | 拥有的责任 | 明确排除 |
|---|---|---|---|
| driver-model | 设备如何注册并由驱动管理 | 设备关系、注册、匹配和绑定生命周期；设备分类关系须与此协调 | 家族 I/O、OS 实现 |
| 现有 driver-class（待迁移） | 当前泛型能力注册不能等同于 Linux class | 按实际调用者归还职责；hwrng 注册和操作生命周期归 hwrng | 不为保留 crate 而发明通用发布模型 |
| driver-os-api | 驱动框架需要宿主提供什么能力 | MMIO/IRQ/DMA 等现有宿主契约 | 调度器/IRQ core 实现、设备管理状态 |

hwrng 排空优先复用已有 RngCompletion 和 host adapter，不新增 os-api 等待
trait 作为先决目标。真正的 class 按 device 分类及已有节点需求设计，不从
泛型能力注册表机械改名，也不为此次 hwrng 迁移实现整套 sysfs/misc 功能。

已有 kfinalize 是 util 层的所有权与异步析构工具，其 Cargo 依赖不包含 ktask/kwork。
需要跨上下文析构时可以复用；实际执行由宿主安装的 worker provider 完成。
这与可移植层直接调用调度器不同，不新增 driver-specific executor crate。

## 2. 目录与 mod 候选

以下目录为早期草案，不是当前实现指令：其中 base/class 的 publication 结构
及 os-api/completion.rs 候选已撤回。hwrng 注册/消费者/同步注销在子系统内部
按共同生命周期组织；真正 class 的落点待 device 关联设计完成后确定。

```text
drivers/base/model/src/
  device/               设备描述、对象引用、回调借用视图
  driver.rs             驱动注册描述和 typed probe/remove 契约
  bus/                  通用总线词汇、实例归属契约
  model/                一个驱动模型实例的唯一管理入口
    registration.rs     注册索引、关系校验和移除登记
    binding.rs          探测、成功提交、解绑与回滚协议
    deferred_probe.rs   等待依赖和重新排队，非通用依赖图
  host.rs               设备语义到宿主资源能力的接入契约

drivers/base/class/src/
  class.rs              class 表、订阅与 hooks
  publication/          注册权、消费者、许可与单项撤销
  source.rs             只读来源契约

drivers/base/os-api/src/
  mmio.rs / irq.rs / dma.rs / clock.rs
  completion.rs         需要补充的一次性完成/等待契约
```

这不是要求一个类型一个文件：publication 内共同维护许可、撤销和 finalizer
的细节应聚合。状态字段、锁和访问方法不按“都是结构体”或“都是 helper”拆散。
model 内的子 mod 是同一状态机的实现细节，不分别拥有锁和公开 Registry。
现有错误、固件描述等按其真实使用者归属，不为了上述示意目录而机械搬动。

具体 PlatformBus 不属于通用 bus mod。将它移到具体总线实现层，与其描述词汇、
匹配规则一起维护；是否独立 crate 由枚举方和具体驱动的真实依赖决定。
Environment 的静态 provider 注册与扩展查找不能继续作为“杂项服务”打包。
保留实际需要的宿主能力接入；没有生产使用的 provider 家族不提前建立动态系统，
其现有抽象及 UT 如何保留/迁移须在对应重构中列明，不静默丢弃。

## 3. 命名调整及理由

| 当前名字/结构 | 候选调整 | 理由 |
|---|---|---|
| DeviceDomain / domain | DriverModel / model | 表达可实例化的整个驱动模型入口，避免 domain 被理解为 IRQ domain、IOMMU domain 或设备所属总线 |
| DeviceCore | 私有 Device | 对象本身拥有设备事实，不再制造“完整设备”和“核心设备”两套身份概念 |
| DeviceRef | 保留 | 明确是设备对象引用，不是运行权或注册凭证 |
| DeviceAccess | 保留 | 明确是回调期借用的访问视图，不拥有设备或绑定 |
| services | host | 是宿主接入契约，不是框架内所有服务的容器 |
| dependency | deferred_probe | 当前承担延后探测，不暗示已经实现任意资源依赖图 |
| owner.rs / PublicationSource | source.rs / PublicationSource | 文件与只读来源角色一致，不再暗示拥有撤销权 |
| PublicationScope | 不作为必需核心类型 | 当前未证明需要在单项撤销之外增加所有设备强制遵守的组级准入 |

名字是本稿候选，不意味着已批准重命名代码。若一种新名称没有消除职责歧义，
宁可先修职责再改名，不以换名代替结构修复。

## 4. 唯一事实与对象拥有关系

| 事实/资源 | 权威来源 | 谁能更改或结束 | 谁可以保留引用 |
|---|---|---|---|
| 设备描述、位置、父关系 | 注册的 Device，描述由枚举输入转交 | 注册入口校验；不提供任意外部修改 | DeviceRef、只读来源 |
| 总线类型 | 具体总线实例及其类型契约 | 模型实例管理注册关系 | 枚举方、设备描述关联 |
| 驱动名称/匹配表 | 驱动注册对象 | 驱动注册管理入口 | 当前尝试及历史发布来源 |
| 设备是否注册/正在注销 | 模型注册记录 | 注册/注销协调入口 | 对外只能查询状态，不复制另一个 online 标志 |
| 当前绑定及运行 Data | 当前绑定记录 | 绑定状态机 | 不交给纯设备引用或消费者保活 |
| 本次发布属于哪个设备/驱动 | 本次尝试的只读关联 | 建立后不改指向 | PublicationSource |
| 单项发布可否使用 | class 单项准入 | 注册权撤销 | 消费者只能取得许可 |
| DMA/IRQ/队列 | 驱动运行资源及相应句柄 | 驱动停机协议与宿主同步释放 | 只在仍合法访问时保活 |

当前绑定查询从模型的绑定关联取得驱动，不在 Device 中维护“最后 probe 的
driver_name”作为第二份事实。旧发布查询旧关联，新绑定查询新关联；这不是
复制设备身份，而是保存不同时间段的真实关系。

内部索引可以存在，但不会为方便索引新增公共设备 ID。表中的对象引用与
只读来源引用同一个 Device；不复制 descriptor/path/driver name 到发布容器。
父关系与控制器创建下游关系仍须分别表达，不能用一个 parent 指针推导全部资源所有权。

## 5. class 负责发布的准入，model 不替所有服务统一关门

单项 Registration 控制自身发布，class 统一实现许可计数、关闭与排空，驱动
不手写计数协议。设备有多个发布时，驱动/子系统逐项撤销并完成自己的收尾。
要求的是退出返回前全部结束，不是发起解绑时所有能力在同一瞬间失效。

共享 PublicationScope 不再作为必需核心类型：当前需求没有要求跨 class 原子
撤销，它也不能替代显式注销；父控制器的服务还可能必须保留到孩子退出。
不得用 model 的 Unbinding 状态直接判定所有 Publication 都不可操作。

旧发布不可复活由各自永久关闭的准入保证；新绑定创建新的发布。设备及驱动
来源保持只读查询，不承担许可计数。具体子系统若确有成组停止需求，应基于
真实用例设计局部封装，不先将它扩散为每个驱动的通用协议。

## 6. 复用 DeferredArc 的边界，而非再造执行系统

已核对 `util/kfinalize/src/lib.rs` 和 `task/kworkng/src/finalize.rs`：构造时准备
carrier，最后强引用释放只转交析构责任，worker 执行 payload Drop。弱引用在
提交时已不可升级；支持的上下文及初始化前提由工具契约规定。

它适合承载“需要在 worker 执行的最终清理义务”，不应直接替换所有 DeviceRef、
Publication 或驱动 Data 的 Arc，更不能把解绑定义成最后一个引用析构。
共享 finalizer 串行运行，payload Drop 不能等待同一 executor 上另一个 finalizer。

经用户确认，退出与析构分开：

1. model 保有成功绑定，显式调用 remove；驱动完成发布撤销和硬件停机。
2. Registration 管理关闭和排空，InUse 归还只计数及通知，管理者执行 hook。
3. 旧 Publication 可保留已停止的 runtime；不强制拆出身份外壳或清理义务对象。
4. 未完成退出就销毁管理凭证是生命周期 bug，不增加后台补做 remove 的机制。
5. probe 失败的构造回滚是受支持路径，必须显式收尾已发布能力及已启动硬件。

不引入通用 PayloadSlot/UnsafeCell，也不要求 DeferredArc 提供 unwrap。
具体资源由驱动在停机时解除；对象最终析构可以延后，不能影响新绑定。
具体接口与诊断方式见 class-withdrawal-design.md，尚未实施。

结论：撤回“再添加通用 driver 异步执行契约”的默认方向，优先复用已有
工具；os-api 新增范围限制为确实缺少的等待/完成能力，不把 worker 框架搬进 base。

## 7. 正常路径及责任交接

```text
枚举方提供发现事实
  → 宿主在旧注册前分流
  → DriverModel 注册 Device，校验总线和父关系
  → 为本次尝试创建来源关联
  → 驱动 probe 初始化资源，准备好后显式发布
  → probe 成功交付 Data，模型提交绑定

解绑：模型串行化该设备的管理操作，阻止本绑定新建下游
  → 调用驱动 remove；控制器通过具体总线停止枚举并注销拥有的下游
  → 驱动按子系统顺序停止提交、唤醒读者、撤销发布
  → 许可、IRQ、DMA 按实际协议安全收尾
  → 显式完成 hook 与运行资源清理
  → 模型结束绑定，设备保持注册
```

发布可以早于 probe 返回，失败必须走同一驱动收尾逻辑。设备注销是额外结束
注册与关联的操作，不与解绑共用一个含混的 Removing/Removed 状态。
remove 保持无错误返回契约，驱动必须在返回前履行退出责任；不增加通用解绑
失败状态或重试事务。硬件故障由具体驱动/总线处理，不授权释放仍被 DMA 使用
的内存，也不在模型中实现设备特有恢复算法。

## 8. 设计 review 范围与尚未完成部分

本稿可评审：crate 边界、mod 聚合、命名理由、事实来源、持有关系，以及复用
已有析构工具的方向。它不授权编码，不把结构通过等同于全部生命周期机制通过。
许可/收尾交错及 Linux 重入约束的进一步收敛见 [退出协议](exit-protocol-v0.1.md)。
等待、实例 DMA、VirtIO 取消及枚举分流的 Interface 见
[真实接入契约](integration-contracts-v0.1.md)。

后续收口工作有三类，不能再靠新增抽象跳过：

1. **并发协议**：具体管理重入规则、单项许可、清理义务执行权与完成等待，
   用确定性交错表证明不会提前释放、重复执行或等待自己。
2. **真实依赖**：VirtIO 库 shutdown/未完成 token 回收、kirq 等待失败前置处理，
   包括 reset 不成功时的资源保留和调用者可观察结果。
3. **集成验证**：固件 DMA 视图、MMIO RNG 接线与实际节点/事件回归，不能以
   UT 或旧 class 桥接代替新模型完整路径。

需求、核心关系已稳定，不再无限扩展功能或反复征求字段选择。剩余问题由
agent 核对事实并形成具体机制；仅真正改变外部行为/范围的取舍再单独说明。

## 9. 集中一致性检查与需求映射

评审对象为本文、退出协议与真实接入契约，早期 v0.1 草案只作调查过程记录。
这是设计自查，不是当前 Rust 实现的 PR 合格结论，也不是人工批准。

### 已修正的问题

| 问题 | 可触发后果 | 修正 |
|---|---|---|
| 退出草稿先释放资源、后运行接收 runtime 的 hook | hook 访问已经失效的运行资源 | 区分硬件停止与资源释放，依赖资源的 hook 完成后才释放 |
| Registration Drop 与 InUse Drop 混同为任意上下文保底 | hardirq 内执行注册表通知或可能阻塞的管理流程 | 注册权管理要求任务上下文；使用许可 Drop 只做允许的计数/通知/义务转交 |
| 只检查 gate/count 就允许 hook 被领取 | 并发 finalizer 越过尚未完成的移除通知 | 完成通知阶段也是领取前提，Registration 在通知结束前保有清理义务 |
| 自动重入检测仍残留在早期接口表述 | 无必要引入任务身份和通用检测系统 | 统一成 Linux 一致的调用前置条件，删除自动检测承诺 |

### 需求覆盖检查

| 需求 | 已有设计承接 | 验证/完成条件 |
|---|---|---|
| R01 注册与绑定分离 | 独立注册状态、绑定记录，同一 DeviceRef 跨解绑 | 无驱动、解绑、重绑、注销四种外部行为 |
| R02 单一事实来源 | 第 4 节权威来源表，来源只关联身份 | 查询一致，无重复可变 driver_name/online |
| R03 回滚 | 驱动构造守卫与正常停机逻辑复用，依赖 P1/P2/P6 的正常收尾 | 发布前后错误注入；不依赖补调 remove 或准备接口 |
| R04 延后探测 | 独立调度记录、代次核对、执行前重新校验注册 | 条件先到/后到/交错、注销后迟到通知 |
| R05 旧句柄隔离 | 每次发布独立准入，关闭不重开 | 保留旧句柄跨重绑，不能访问新 runtime |
| R06 在途退出 | 关闭、唤醒、排空、硬件停止、hook、释放分别负责 | 退出协议第 7 节交错；不得把引用归零当硬件停止 |
| R07 多实例 | 每实例资源/作用域；IRQ action 级退出 | 一个退出，另一个继续消费/派发 |
| R08 上下文/并发 | 单设备管理串行化、锁外回调、P1 可靠等待 | 无自等待、清理一次、并发请求复核状态 |
| R09 宿主边界 | os-api 实例 DMA/完成契约，host 实现 | 依赖审查、不同设备 DMA 视图、配对回收 |
| R10 真实 hwrng | MMIO 候选路径、显式注册、entropy 消费 | 真实资源及解绑/重绑，不能只验 legacy class |
| R11 渐进迁移 | 旧注册前分流，保留旧默认 VirtIO 后端 | 撤掉旧 RNG 注册仍能发现，其他设备回归 |
| R12 现有系统接口 | 保留 input/DRM 投影和事件，不虚构 RNG 节点 | 迁移前后实际节点/事件清单比较 |
| R13 扩展范围 | 真实用例驱动，未用 PM/hotplug/module 不提前实现 | 无静默删功能；不能以仅有接口宣称功能已实现 |

### 历史检查发现的两处接口缺口及曾考虑的方案

以下保留设计演进记录，整树准备及类型擦除方案已由第 12、13 节替代，不再
作为待完成的接口要求。当前方案的行为核对见第 14 节。

1. **驱动内部退出准备怎样交给管理流程。** 当前文字要求所有可能失败的等待
   准备发生在关闭前，但 DriverOps 只有 probe/remove，并未落实携带发布、IRQ
   等等待凭证的调用契约。需要明确可失败准备与不可逆 remove 的交接，而不是
   让实现者在 remove 中临时猜测分配失败如何处理。
2. **控制器创建的下游与静态父关系如何结束。** 已明确二者不同，但尚未给出
   注册权、关闭新增下游及孩子退出的接口。不能仅凭图中的 parent 关系就
   认定整棵子树归当前绑定，也不能私自加“只允许叶子解绑”的限制。

以上是集中检查时的缺口。[退出协议第 10、11 节](exit-protocol-v0.1.md)
现已补充候选交接契约：管理认领后准备、准备结果由同一任务交给 remove、
下游注册提交与认领串行化、下游先退出而父控制器服务暂时保留。

该补充明确修正了“先关闭父设备全部操作，再注销下游”的过强顺序；通用 model
负责生命周期协调，具体总线负责下游次序。不新增绕过关闭 gate 的访问权限。
准备失败只保证没有不可逆设备变化，不保证其他管理调用完全不受短暂串行化影响。

这两项已有具体候选方案，待集中评审，不再作为未分析的空白接口。仍不能标记
完整设计已经批准。[退出协议第 12、13 节](exit-protocol-v0.1.md) 进一步明确：
准备结果用独立的非 Send 类型擦除，由原任务配对原绑定执行；活动注册权丢失
只记录违约并保留权威记录，显式关闭负责收尾。最后 model 所有者违约丢弃时，
保留活动状态及依赖，接受异常资源保留而不是冒险释放硬件资源。这是需在集中
评审中明确接受的安全取舍，不宣称无泄漏，也不把它当成成功退出。

至此两处缺口具备可评审的具体契约；下一步集中审阅第 10—13 节，不再继续
扩展设计文件。关联类型、装箱及等待凭证的实际编译/交错验证列为实施验收，
当前只做了源码与设计核对。整体设计获确认前，不生成可开发 tickets。
库补丁、IRQ 算法及 QEMU 闭环的实际测试属于之后实施验收，不能由文档自查替代。

## 10. 历史评审：整树认领导致下游自等待

本轮发现一项阻断实施的接口问题，先停在这一项，不以新增测试条目掩盖。

第 10—13 节退出协议已经要求父计划认领整个拥有集合，但又要求具体总线
按自己的次序注销下游。如果总线回调调用普通 unregister，后者会等待父计划
持有的子设备管理权；父计划正在等回调返回，形成自等待。准备结果携带正确
绑定引用不能自动消除此问题。另一个缺口是：当前 prepare/remove 两段交接
尚未给出“父服务仍可用时运行下游退出”的回调位置。

### 推荐修正方向

- 普通注销入口负责取得管理权；计划内部执行入口只消费已认领、已准备的子项，
  不重新认领、不重新准备等待资源，也不通过线程身份放宽重入限制。
- 退出协调明确区分“下游阶段”和“本设备阶段”。下游阶段停止并同步枚举源，
  由总线逻辑驱动已经准备的孩子退出；全部孩子完成后，model 才关闭父作用域
  并调用父设备的本地 remove。
- 给下游阶段的只是本次计划所拥有孩子的受限执行视图，不是可管理任意设备
  的 DriverModel 引用。不能绕过准备集合去追加注销其他设备。
- 下游阶段不持有子设备回调所需的父事务锁。若子退出未完成，不执行父 remove，
  不把父 Data 移出绑定或当成普通局部变量析构。
- 叶子驱动不需要写空的下游处理代码；具体回调封装应聚合到总线/下游所有权
  模块，而非把控制器专用操作无条件扩散给所有 hwrng 驱动。

这条方向不等于正式接口已经闭合：还需要明确下游阶段如何与当前 DriverOps
适配器交接，避免给整个框架再加一套通用事务引擎。本轮不批准进入实施拆票。
修正主流程图是消除文档顺序冲突，不是该接口已经实现的证据。

## 11. 调整依据：对照 Linux 撤回整树准备

用户要求参考 Linux 的处理流程。本轮读取本地源码得到下列事实，而不是
仅以类型名称类比；路径均相对于 `/root/linux-stable`。

| 源码 | 实际责任 |
|---|---|
| drivers/base/dd.c，__device_release_driver / device_release_driver_internal | 锁保护单设备解绑；对 device links 的消费者协调会解锁、处理、重加锁并复核绑定；不能概括成核心完全不管依赖 |
| drivers/i2c/busses/i2c-designware-platdrv.c，dw_i2c_plat_remove | 先 i2c_del_adapter，后禁用控制器并关闭时钟；父 remove 内可以同步退出不同的孩子 |
| drivers/i2c/i2c-core-base.c，i2c_deregister_clients / i2c_del_adapter | 总线模块注销 clients，并区分普通 client/dummy 的顺序；随后拆适配器资源 |
| drivers/pci/controller/pci-host-common.c，pci_host_common_remove | PCI 自己取得 rescan/remove 串行化锁，再执行 stop_root_bus/remove_root_bus |
| drivers/pci/remove.c，pci_stop_bus_device / pci_stop_and_remove_bus_device | 按 subordinate 关系递归停止，先孩子后父；已持总线锁的内部函数与负责加锁的外部入口分开 |
| drivers/base/core.c，device_unregister | device_del 后 put_device；结束注册与对象最终释放不是同一步 |
| kernel/sched/completion.c，do_wait_for_common | 用栈上 DECLARE_SWAITQUEUE 登记和等待，不为每次等待临时堆分配登记节点 |

Linux 同样不允许 remove 递归解绑同一个设备，但不禁止所有跨设备注销。
上述总线代码不是通用核心预先认领整棵树、分配每个子设备的退出计划后再执行。
I2C adapter 的历史实现还等待对象引用归零，源码自身有解耦 TODO；不将这一点
照搬为本框架等待所有 DeviceRef 的要求。

### 设计方向调整，而非直接宣布替代方案可实现

第 10 节所述自等待真实存在于我们的候选协议，但“再增加子计划专用执行接口”
并非唯一解。整树认领与两阶段 DriverOps 主要由宿主可失败的等待登记向上推导；
应先评估在 os-api/host 层提供可靠的同步等待，能否避免将该成本扩散到所有驱动。

优先评估更接近 Linux 的职责划分：

1. model 串行化单设备管理，不默认认领整个下游集合。
2. 总线/控制器拥有下游注册，负责停止枚举并串行化自己的注册/移除入口。
3. 父 remove 内先调用总线的注销操作，逐个完成孩子退出，再停止自身硬件。
4. 内外入口是否重复取得同一管理锁由具体模块明确，不能靠任务身份自动跳过锁。
5. class 的作用域只管它保护的能力；不得关闭孩子收尾仍需的父服务。因此也需
   同时审视 model 统一在父 remove 前关闭作用域的策略，不能只删整树计划。

此方向不承诺目前的 kpoll/PreparedTaskWait 已经支持无分配同步登记：后者
只保证准备后的 park 不分配，不替调用者解决等待登记。需要核对宿主能否提供
生命周期安全、无丢唤醒、无临时可恢复分配失败的登记，再决定取消哪些准备接口。
若确需前置准备，应优先局限于等待/资源适配层，不直接恢复全框架整树事务。

第 10—13 节退出协议中的整树准备、RemovePreparation 与受限子计划执行因此
降为待比较方案，暂不据此拆实现票。注册与绑定分离、身份引用不代表操作权、
资源停止后释放以及下游先于控制器收尾等不变量保持不变。需求基线没有变化。

## 12. 前置能力成立时的精简框架设计

用户允许列出全部已识别前置后，按其成立继续设计，将实现排序留到 tickets。
本节采用 [真实接入契约第 11 节](integration-contracts-v0.1.md) 的 P1—P7，
不表示这些能力已实现或已验收。同步等待可靠仍不等于硬件停机必然完成。

### 四个职责，保持普通 probe/remove

| 对象/模块 | 职责 | 不负责 |
|---|---|---|
| model | 设备注册、单设备管理串行化、匹配、绑定提交及解除 | 总线特有子设备退出顺序、业务请求取消、宿主等待节点 |
| 总线/枚举模块 | 总线实例与创建权限、发现设备、下游注销和本总线管理锁规则 | 因 parent 相同就取得其他所有者的设备 |
| 驱动及其 Data | 初始化、持有运行资源/注册权、remove 和 probe 失败时完成收尾 | 为整个框架准备退出计划、自己实现通用许可计数 |
| class | 发布注册、消费者句柄、操作许可、撤销/排空及 hook 完成 | 推断硬件是否停止、替驱动遍历所有发布或孩子 |

DriverOps 保持 typed probe/remove，不增加 prepare_remove、RemovePreparation
或通用 remove_children 回调。Data 仍由当前绑定拥有，remove 获得回调期访问；
正常返回表示驱动应承担的退出已经完成，之后才能释放 Data、提交 Unbound。
具体 remove 可以调用总线注销和 class 撤销的普通同步接口，借用可靠宿主等待。

### 管理和服务分开

model 只认领当前设备的管理操作，短状态锁外执行回调/等待。竞争管理请求
等待后重新校验，不提前认领所有孩子；不同设备的操作不因全局回调锁而串行。
同一回调递归等待当前设备仍是违约，不增加任务身份或自动绕锁机制。

进入 Unbinding 时，当前绑定的下游创建权限关闭，迟到枚举结果不能成功提交；
但现有 publication 的许可由 class 撤销控制，父服务并不自动失效。总线还需
停止并同步枚举工作，避免其继续访问将被释放的控制器。创建权关闭不等于
等待枚举完成，也不等于所有驱动操作都被一个 online 位关闭。

若孩子管理操作已在进行，父 remove 可按总线契约等待它结束，但不得持有孩子
完成所需的控制器事务锁。孩子不得同步等待正在调用自己的父 remove 完成。
总线已有外层管理锁时，内层 helper 不重复取得它；这属于具体模块接口，不是
model 的通用“绕过管理权”入口。参照本地 PCI 的 locked/internal 函数分工。

### 两条具体流程验证职责

**叶子 hwrng：** model 调用 remove → 驱动设置停止状态并唤醒阻塞 read →
撤销 hwrng 发布并排空消费者 → 按 transport/IRQ 契约确认停机、同步 handler、
回收未完成请求 → 完成依赖资源的 hook → 释放资源 → remove 返回。
硬件停止与 IRQ 同步的精确先后由传输契约决定，不能拿消费者排空替代二者。

**控制器：** model 调用父 remove → 总线停止并同步枚举 → 总线调用孩子的普通
注销入口，由 model 串行化各个孩子 → 孩子完成自己的 remove → 结束下游总线
注册 → 父驱动再撤销自身服务、停止硬件并释放资源。孩子退出期间可继续使用
尚未撤销的父服务。该流程解释扩展位置，本阶段不因此实现 PCI/I2C 驱动。

这与 Linux DesignWare I2C remove 中先 i2c_del_adapter、后禁用控制器的责任
关系一致；不照搬 I2C 历史上的等待所有元数据引用消失。没有“只能解绑叶子”限制。

### 失败与所有权仍有硬约束

- probe 中发布立即可见，不引入原子提交全部能力的模型事务。后续失败由驱动
  先停止/唤醒并完成已发布能力与资源的回滚，再返回 Err；框架不会补调 remove。
- parent 仅描述拓扑；拥有关系决定谁负责注销。总线退出后不能留下仍需访问
  已释放控制器的子设备，引用存活也不能变成继续使用硬件的权限。
- remove 正常返回后旧发布全部失效、资源已安全收尾；新绑定创建新运行对象。
  保留 DeviceRef/Publication 只保留身份或失效外壳，不阻止正常解绑。
- 注销比解绑多一步结束设备注册；纯解绑仍保留原 DeviceRef 身份，不伪造设备
  消失事件。模型不根据硬件 reset 错误自动提交成功或尝试旧框架接管。
- 显式退出是正常路径。资源保留的违约保底不冒充成功、不作为无泄漏验收依据。

### 本轮删去的复杂度

不再采用：整树管理认领、任务局部子退出计划、通用准备关联类型、准备结果类型
擦除、强制两级 publication gate，以及为了内部计划新增的特殊子注销入口。
保留单项 class 的许可/撤销/收尾协议；仍需做确定性交错测试，不因设计精简
而省略安全证明。早期相关章节是被替代的候选过程，不作为实施要求。

## 13. 核心对象与接口契约

本节细化第 12 节，不新增生命周期阶段。表中新增名称均为候选角色名，不表示
已重命名代码；Rust 字段、泛型和内部索引不作为公共契约提前固定。

### 设备与绑定：谁持有，给谁用

| 对象 | 内容与持有关系 | 使用者与有效期 |
|---|---|---|
| DeviceDescriptor | 枚举输入的设备事实：所属总线实例、匹配数据、拓扑父关系、资源描述及 DMA 约束 | 枚举方构造，注册时校验并转交；不是另一份可变设备运行状态 |
| 私有 Device / DeviceRef | Device 拥有描述与稳定身份；DeviceRef 共享引用同一对象 | 框架、枚举方和只读来源可保留；解绑不换身份，注销不强制消灭旧引用 |
| DeviceRegistration | 指向已注册记录的管理凭证，不另持一份描述或绑定状态 | 主机/总线枚举方保存，用于显式注销；普通消费者不持有，丢弃不等于执行 remove |
| 私有绑定记录 | 关联本次驱动注册对象，持有成功 probe 的 Data 及管理状态 | 仅 model 改变；DeviceRef 不保活 Data，解绑结束后不再是当前绑定 |
| DeviceAccess | 当前回调对设备及宿主能力的借用视图，创建的资源关联正确设备 | probe/remove 借用；不能保存该借用到异步任务，不通过它恢复旧绑定 |
| DriverOps::Data | 驱动私有运行状态、资源及它负责撤销的注册权 | probe 交给绑定，remove 借用并结束运行职责；不是设备描述容器 |

总线实例提供总线类型，设备不再并列保存可互相矛盾的 bus 类型与实例。
DeviceRegistration 与 DeviceRef 分开是权限/生命周期差异，不是为相同字段加
一层 Registry 包装。注册权如何被具体总线聚合由总线模块决定，model 不再
另外维护一份能够自动执行整树退出的驱动私有计划。

主机根注册与绑定创建的下游具有不同归属；在创建时明确记录，而非事后从
parent 猜测。异步枚举若要跨回调使用创建权限，应持有指向原创建关系的受限
能力；model 在提交时检查该关系是否仍有效。不能只拿 DeviceRef 就重新取得
创建权限，也不能通过新的当前绑定让旧权限复活。

### 管理入口的最小可观察契约

| 操作 | 成功意味着什么 | 失败/竞争约束 |
|---|---|---|
| 注册设备 | 描述通过校验，设备纳入管理，返回注册权及可分享的设备引用 | 未注册对象由调用者负责；不能留下半注册记录，不能在退出中的创建者下提交 |
| 探测/再次绑定 | 在仍注册、未绑定的设备上完成一次匹配和 probe，成功 Data 只提交一次 | 正常失败和依赖未就绪不同；不通过重建设备身份实现重试 |
| 解绑 | 本次 remove 结束、运行职责结束，设备仍注册 | 无绑定时是无须回调的完成；并发请求串行化后复核，不重复 remove |
| 注销设备 | 先结束绑定，再结束该设备注册；旧引用只供身份查询 | 已注销不能重新 probe；重复请求不重复清理；不能自动以 parent 推导整树删除 |
| 查询 | 从权威记录返回设备/绑定状态或身份事实 | 结果是观察，不授权硬件操作，也不授权注销 |

管理入口先验证目标属于本 model、调用上下文合法及权限有效，再开始不可逆
动作。这里不增加 prepare_remove，而是使用 P1 的正常等待保证。正在执行的
probe 与注销竞争时，由管理协议承接 probe 的结果：失败必须已回滚；成功的
Data 必须执行正常 remove，不能因为不再允许绑定提交就直接 drop 活动资源。

延后探测只是未绑定设备的一项重试原因/调度记录，不是新设备身份，也不占用
一份成功绑定的 Data。条件通知与登记采用检查/登记/复查或等价序列化协议，
执行前重新核对注册及当前状态；迟到通知不能让已注销设备恢复。具体依赖键
沿用实际用例，不先设计通用 provider 生命周期或依赖图调度器。

### class：区分元数据、注册权和操作许可

| 对象/操作 | 契约 |
|---|---|
| PublicationSource | 只读关联设备身份与本次驱动来源；不提供停机、撤销或准入控制 |
| Registration | 唯一发布注册权；驱动/子系统保存并显式撤销，消费者 clone 不获得该权利 |
| Publication | 可复制的消费者句柄，保有身份及运行外壳；是否能执行操作须重新取得许可 |
| InUse | 单项发布的一次在途操作许可；归还更新计数，不在任意上下文执行睡眠清理 |
| 关闭/撤销 | 拒绝该发布的新许可、移出 class 表并通知；已取得许可者仍受保护 |
| 排空/完成收尾 | 可靠等待最后许可归还，完成一次 class hook；此后驱动才能释放 hook 仍需的资源 |

单项 gate 的关闭与 acquire 必须线性化，不能先读 online 再无条件加计数。
is_available 只供观察，不能替代 acquire；不因 Device 注册或绑定状态变化而
自动否决尚未撤销的 publication。现有 source.is_online 检查因此需要改造：
发布资格在发布入口由创建者权限校验，运行资格在 publication 内校验。
来源本身既不缓存独立在线位，也不兼任可变的绑定状态容器。

本阶段 model 的设备关联发布通过 probe 的 DeviceAccess 入口完成；该借用
视图不能跨回调保留。probe 正在执行时，同设备 remove 不能并发执行，因此
不能只在 publish 之前读一次绑定状态，然后在无保护的异步任务中完成插入。
注销请求即使已经阻止新的探测，也必须等待正在执行的 probe 交付结果并完成
对应回滚/remove。remove 视图不允许新发布。

这没有限制独立使用 class 的发布方；其发布/退出由自己的所有者协调。当前
不增加可复制、跨任务的 model 发布权限对象。未来若有运行期异步增删能力的
真实子系统，再明确它的发布管理协议；不能凭一份只读 source 让旧绑定复活。

正常退出采用同步撤销/排空；若某子系统需要先关闭、再取消工作、最后等待，
class 可提供这三个动作的组合与分步用法，共享同一状态，不另造业务事务对象。
同步等待不得持有消费者完成所需的锁。Registration 的非等待 Drop 保底不等于
完整驱动退出，调用方不能用它替代硬件停止及同步；清理义务策略仍遵守第 6 节。

### 用实际 hwrng 约束接口，而非为了将来加类型

本地 Linux virtio-rng 的 remove_common 先标记 removed 并唤醒 read，再注销
hwrng，随后 reset/del_vqs；本设计对应的是“先让在途 read 能退出，再等待排空”，
不是复制它的字段名。不能先等待一个只有未来 IRQ 才能唤醒的 read，再执行 stop。

新 hwrng 的最低验收链为：注册设备 → 匹配 probe → 获得 P4/P5 的实例资源 →
发布并消费 → 并发 read 下解绑 → 旧 Publication 拒绝新操作 → 同一 DeviceRef
重绑获得新 Publication → 注销。另加双实例隔离、probe 发布后失败回滚及延后
探测通知交错；这些能验证当前职责，不需要新建 PCI/I2C 框架才能证明可扩展。

### 本轮设计结论

核心对象、权限和退出调用方向已形成可集中评审的候选，前置能力按 P1—P7
列出，不再因为底层尚未完成而引入上层替代协议。仍不等于设计获批或实现通过；
后续拆票应将这些可观察行为作为验收，而不是按每个类型拆一张机械搬迁票。

## 14. 精简方案的行为核对与评审结论

核对依据为第 12、13 节及 P1—P7 成立的假设；不是已运行的 UT。
本地 Linux hwrng_register 立即加入可选来源，hwrng_unregister 在移出列表后
等待 cleanup_done；virtio-rng 的 remove_common 先唤醒读者再注销。下面沿用
这些责任和时序，不要求移植 Linux 的链表、名字去重或全部系统 ABI。

| 场景 | 设计给出的结果 | 责任归属 |
|---|---|---|
| probe 发布后消费者立即进入 | 允许；发布之前 runtime 必须可服务，不能等 probe 成功才初始化必需字段 | 驱动初始化、class 单项准入 |
| 发布后 probe 失败 | 先唤醒/终止在途操作，撤销并排空，再释放资源并返回 Err | 驱动回滚，class/P1/P2/P6 提供收尾能力 |
| probe 与注销并发 | 不并发执行同设备 remove；成功 Data 被正常退出，失败已回滚，注销之后不能被迟到提交复活 | model 单设备管理 |
| RNG read 阻塞时解绑 | 停止标记使新 read 立即失败，唤醒旧 read，再排空；不依赖未来熵 IRQ | RNG 与 class |
| 旧 Publication 跨重绑保留 | 旧 gate 永久关闭；新发布拥有新的运行对象，不查询“当前绑定”恢复旧句柄 | class 单项状态、只读来源关联 |
| 子 remove 需要父控制器服务 | 父服务保持到孩子退出；不持父事务锁等待孩子 | 控制器/总线退出次序 |
| 枚举结果与父退出并发 | 先提交者由总线注销；创建权限关闭后的提交失败，由枚举方回滚未注册对象 | model 注册校验、总线管理串行化 |
| 一个 hwrng 解绑、另一个继续 | 发布和资源分别归属本实例；不整体关闭共享 IRQ，不混用 DMA 后端 | 驱动资源、P2/P4/P5 |
| 依赖通知晚于设备注销 | 通知可到达，重试执行前检查后不再 probe | deferred_probe 与注册状态 |
| class hook 与资源释放交错 | 需要 runtime 的 hook 完成后才释放对应资源，等待不在 class 表锁内执行 | class 收尾与驱动资源生命周期 |

状态：用户确认拆分记账：01A（内核 Completion、ktask adapter 与现有调用方迁移）已合入；01B（新驱动框架可移植等待契约、真实宿主与测试 adapter）未完成，C10 在新框架中的接入闭环仍需验收。原 01 不标记整票完成。
推进顺序为 01A → 02 独立验收 → 01B/03 局部设计 → 01B 接入 → 03 撤销闭环。
整个 Work/Queue drain 等组合操作无分配不是本票已完成保证，详见 [验收记录](completion-implementation.md)。

## 1. 来源与问题

用户指出内核已有 completion，要求先判断现有机制问题；随后提出参考 kwork：
由外部负责 work 的存储生命周期，提交不逐次申请内存，并要求按系统 skills
整理 Ticket 01 需求。方向是完善现有能力，而不是新增一个完成框架。

已核实事实：

- `task/kpoll/src/completion.rs` 已有令牌语义、complete_all、reinit、poll 登记。
- `task/kpoll/src/source.rs` 使用 SmallVec 槽表，扩容会 try_reserve，登记身份也
  可能耗尽；`task/kpoll/src/registration.rs` 的所有者容器同样可能扩容失败。
- `task/ktask/src/irq_wait.rs` 已有同步等待桥，但沿用可失败的 poll 登记。
- `task/ktask/src/future/mod.rs` 的 block_on/PreparedTaskWait 创建 Arc<KWaker>；
  仅取消登记表扩容并不自动使整个同步等待无分配。
- `arch/kirq/src/runtime/manager.rs` 在 action 已移除后等待失败会 panic。
  这个失败分支当前就存在，不是将来支持内存分配失败后才会出现。
- `task/kpoll/ut-tests/kpoll_unittest.rs` 已覆盖令牌、complete_all/reinit、延迟
  唤醒和登记行为，不能因改造静默删除这些语义。

本地 Linux 的 `kernel/sched/completion.c` 使用调用方栈上 swait 节点等待；
`include/linux/swait.h` 定义节点和队列。kwork 的 borrowed Work 由外部提供
稳定存储，准备后不逐次提交分配。这些是设计参考，不强制照搬内部结构。

用户补充 waitqueue 也可借鉴。核对 Linux `include/linux/wait.h` 的
___wait_event：在调用栈上定义 wait_queue_entry，prepare_to_wait_event 登记，
正常结束通过 finish_wait 收尾；可中断路径也有对应摘链处理。一般 waitqueue
等待调用方的条件，completion 自己维护令牌/完成态，二者不能直接互换。

本仓库 `task/ktask/src/wait_queue.rs` 使用 event-listener 的 listener!；锁定
版本 5.4.1 的宏确实创建 StackSlot 并固定地址。此前“WaitQueue 不能直接当作
无分配替代”不是否认它使用栈上 listener：Event 内部初始化、选用的登记后端
以及 block_on 创建 KWaker 仍需分别核对。栈上 listener 不等于等待全路径无分配。
设计时应并列评估现有 WaitQueue、Linux waitqueue/swait 与 kwork 的生命周期
经验，优先复用实际可用机制；不因此扩展成本票必须重构全部 WaitQueue。

## 2. 目标与范围

### 先按等待语义分类，不按 completion 名称合并

用户进一步要求区分驱动需要的 completion 与 kpoll 中的实现。实际调用显示：

| 使用场景 | 权威条件在哪里 | 所需语义 |
|---|---|---|
| hwrng 的 RngCompletion::wait_until/notify | 驱动请求状态、可读数据或错误/停止条件 | 通知只提示重新检查条件，不存完成令牌，也不表示 DMA 成功 |
| block 的 wait_completion/notify_completion | 请求结果由驱动保存，通知记录永久终态 | 一次终态发布，等待后可读取结果；不因重复通知变成多个结果 |
| class 退出排空/hook 完成 | class 的许可计数与清理状态 | 本次退出的一次性完成，不等待纯句柄引用归零 |
| kirq 在途归零 | kirq 的在途状态 | 现有协议会 reinit/complete_all，不能直接替换成永不重置的业务对象 |
| kpoll::Completion | 自身 done 计数/终态 | Linux-like 完成令牌及 complete_all，登记当前通过 PollSet 接入 |

据此，驱动等待不只有一种语义；特别是现有 RngCompletion 更接近条件等待，
不能因为名字相同强行改成消费 completion token。反过来，kpoll::Completion
确实已经有完成语义，不是仅有 readiness 广播；其位置/底层依赖可重评估，
不能据此称它与通用同步 completion 完全无关。

Ticket 01 以完成同步原语及其宿主等待为核心，不把条件等待、业务结果、请求
状态机或所有 poll 语义打包成一个新的 Completion。是否将原语从 kpoll 独立、
poll 如何适配、是否共享等待节点机制，属于后续设计比较。保留语义不等于必须
保持原 crate 位置，也不等于同时保留两份完成状态。需求仍待整体确认。

补充核对：当前 block_on 在首次 poll 前无条件调用 KWaker::new，内部执行
Arc::new。因此每次正常进入 block_on 都分配一个 KWaker，即便 future 首次
poll 就 Ready；不是每轮 poll 或每次唤醒都再分配。pin!(future) 本身是栈上
固定地址，Arc::clone/Weak 克隆也不是这里的新增对象分配。
WaitQueue::wait_until 把条件检查放在传入 block_on 的 future 内，所以即使
条件一开始就满足，也已经经过这次分配；IRQ 等待桥自身则有 try_wait 快路径。

KWaker 包含弱任务引用及防丢唤醒的 woke 状态；Arc 支持 future 保留/克隆 waker
后仍可安全通知。不能只替换为栈裸指针，或断言通用 block_on 的这个分配必然
可以直接删除。其调用者还包括 sleep、任务和 softirqd 等，通用 block_on 改造
应独立评估影响；不因本票发现此成本就自动纳入全部异步执行路径的重构。

本票要求同步 completion 等待不继承这次逐调用分配；宿主可复用
已有阻塞/唤醒能力或另行提出必要的局部前置支持，不能要求驱动自行绕过。
用户对此分配成本表示担忧，不视为已批准重构全部 block_on 或确认 Q1/Q2。

目标：合法的内核同步完成等待不因临时等待资源申请或登记容量耗尽而失败，
使退出流程可以等待在途访问结束，而不必增加驱动级准备事务。

调用者是宿主任务中的同步等待者、任务/IRQ 中的完成通知者、已有 poll 适配
调用者，以及通过 os-api 使用能力的驱动框架。硬件是否最终完成不由本机制保证。

交付现有 Completion 的必要增强、宿主同步等待入口、可移植契约及测试 adapter
闭环。须验证真实任务阻塞/唤醒，不能只交空 trait 或状态机 mock。IRQ action
释放流程迁移属于 Ticket 02，class 迁移属于 03。

非目标：重写调度器、全部 PollSet/WaitQueue、poll/epoll 用户或 workqueue；
不新增 NMI、超时/信号可中断等待、强制终止线程、硬件超时恢复或全局 OOM 策略。
这里“不重写全部 poll 用户”是避免无依据扩大范围，不是提前禁止修改其共享
登记实现；是否统一底层由第 8 节的成本收益比较决定。
现有可取消 poll 登记仍须兼容，非目标不等于删除已有功能。

## 3. 需求及验收

用户已授权按第 7 节范围设计实现。现有行为是兼容证据，不代表批准所有内部实现。
下表保留需求标识；C02/C11 的原语证据与组合操作剩余分配必须分开验收。

| 编号 | 来源 | 行为要求 | 可判定验收 |
|---|---|---|---|
| C01 | 用户要求复用现有 completion；P1 | 完善现有机制，不引入两份独立完成状态 | 同步与保留的 poll 使用者观察同一令牌/终态 |
| C02 | 用户 kwork 类比；Q1 已确认 | 初始化就绪后，同步 wait 全路径及完成通知不申请堆内存，不因登记 ID/容量耗尽失败 | 观测目标路径分配次数；拒绝新增分配后，已就绪任务与对象仍能等待/通知 |
| C03 | 现有令牌语义 | complete 增加一个令牌，多次调用可累积；try_wait 成功消费一个；唤醒不等于消费 | 多等待者竞争一个令牌仅一个成功，N 个令牌不凭空增减，保留现有计数边界 |
| C04 | 现有 complete_all/reinit | complete_all 保持完成态，当前与后到等待者均可完成；合法 reinit 恢复未完成 | 前后到达、多等待者、重复完成、安全重置；不支持上一代等待仍依赖状态时任意重置 |
| C05 | P1/R08、Linux 等待协议 | 完成先到、登记并发完成、唤醒早于睡眠、虚假唤醒均不丢失完成或提前返回 | 确定性交错测试，检查返回与令牌结果，不靠 sleep 猜时序 |
| C06 | 用户生命周期类比、P1 | 等待存储在使用期间有效，返回后不再被通知路径访问；重复等待无残留登记 | 暂停并发通知与摘除，验证返回和访问顺序；连续等待无活动记录积累 |
| C07 | P1/R08、现有 IRQ 调用 | 阻塞等待只在可睡眠任务上下文；完成支持任务/IRQ，不睡眠；不持阻止完成的锁等待 | 实际任务/IRQ 测试；非法上下文不睡眠、不留下登记，报告方式留到设计 |
| C08 | 同步基本契约 | 完成前按协议发布的数据在成功等待后可见 | 跨 CPU 发布/等待读取测试及内存顺序审查，无未同步的数据访问 |
| C09 | 已有调用者、用户要求评估维护成本 | 保持 poll 登记、取消和通知的正确行为；是否统一底层登记机制由设计评估，不默认保留两套 | 原测试及相关调用者回归，必要接口迁移明确；迟到 waker 不指向失效存储 |
| C10 | 驱动边界硬规则、P1 | 驱动只见可移植完成/等待契约，不直接持有 ktask/kirq 类型，不负责准备整树退出 | 依赖审查，测试 adapter 与实际宿主完成行为一致 |
| C11 | 用户对 block_on 分配锁依赖的担忧 | 合法同步等待与内建通知路径不为登记、停车或收尾而进入堆分配器，不引入等待对分配器的反向依赖 | 审查创建到返回的调用链、锁序及分配/释放路径；原语自身不分配/释放堆对象，回归防丢唤醒握手 |

C02 推荐边界：完成对象及任务初始化允许遵循既有分配失败策略；进入同步 wait
后，登记、阻塞所需辅助对象、虚假唤醒后继续等待、退出清理均不得新增堆分配。
不允许把每次 wait 所需分配挪到紧邻的包装函数而声称达标。调用方预置存储须
是明确初始化/生命周期契约，不是驱动退出前为每个设备新增 prepare 阶段。
存储放栈上还是嵌入其他对象，属于设计选择。

本轮讨论进一步明确为何不能只禁止登记扩容：block_on 在首次 poll 前创建
KWaker，使同步等待依赖分配器；每次退出释放临时堆对象也可能再次取得分配器锁。
因此建议 C02/C11 一并检查等待自身的分配和释放，而非只统计 alloc 调用。
允许共享已存在对象的引用，但不能让本次等待退出时最后一次引用释放隐含触发
本应仍存活的任务/完成对象销毁。所有者的合法最终销毁不属于等待路径无分配保证。

现有代码尚未证实由此形成死锁，不能把锁竞争直接等同于死循环。没有堆依赖
也不表示可持有自旋锁、关中断或禁止抢占等待；C07 的可睡眠前提不变。通知中的
任意外部回调仍须遵守各自上下文契约，本票不能替任意调用方证明其回调无分配。

C03 保留令牌结果，不额外要求每次只唤醒一人。当前 complete 广播唤醒；若
改变公开返回的通知计数等可观察行为，需明确迁移，不当作纯内部优化。

## 4. 异常、兼容与生命周期前提

- 不以跳过等待、假成功、忙等或把可恢复登记错误改成 panic 满足可靠性要求。
- 完成永远不发生时可以一直等待；本票不保证退出期限，也不释放未停机资源。
- 完成对象必须覆盖合法等待/通知期间；不支持销毁仍被使用的对象后继续等待。
  具体借用/拥有约束留到设计证明，不能留下悬空引用。
- is_completed 不是消费令牌或授权释放资源；现有 complete_all_defer_wake 的
  锁外通知使用场景需有等价契约，不能把回调移回外层锁中执行。
- 不绝对冻结旧函数签名；必要调整须更新受影响调用者，不允许新旧入口状态矛盾。

## 5. 实现建议与需求分开

侵入式链表、调用方栈节点、Pin、唤醒句柄以及内部 mod 划分属于设计决定，
已记录于 `completion-implementation.md` 和新 crate 的 `docs/design.md`。
重点是存储和机制的生命周期责任可证明，不把 kwork 执行/取消状态机搬进来，
也不让 Completion 依赖 kwork。
只让链表无分配而在 wait 中创建 Arc<Waker> 不满足推荐 C02；把所有 poll 用户
强制改成同步栈节点超出推荐 C09。

## 7. 范围确认记录

用户最新指令明确要求现有 Completion 全部走新的机制，不增加驱动专用版本。
据此确认 Q1 的完整同步路径目标，并选择替换旧 Completion 后端，而不是长期
并存两套 Completion。通用多源 poll 和任意 Future 的 block_on 不因此全部重写。
源码核对发现 pidfd 只需要退出 readiness，迁回 PollSet；其余 Completion 同步
使用者迁到独立同步原语。RNG 保持条件广播，通过同一等待节点机制实现，不能
错误替换为单个可消费令牌。回调、请求、工作快照的业务存储分配不自动归零，
必须与等待机制本身区分并在验收中列明。

以下保留先前问题和讨论依据，已由上述指令收口：

- Q1：是否要求初始化就绪后的整个同步 wait 路径不再堆分配，而不仅是登记表
  不扩容？用户在讨论 block_on 的锁依赖风险后答复“好的 继续”，支持继续
  按完整同步路径消除分配依赖的方向收敛；具体条款仍随本稿整体确认，不推断
  为允许改造全部 block_on 调用者。
- Q2：用户明确不预先同意保留两套，要求根据修改代价和收益判断。因此撤回
  “先固定旧 poll 后端不动”的建议，改为设计阶段必须比较的技术选择，不再
  要求用户提前选择内部实现。同步与 poll 的正确行为仍需兼容，不能混为后端冻结。

其余按本文范围提交确认；超时/信号中断等新增能力不自动纳入。

## 8. 统一登记机制的成本收益初查

现有使用者的失败时序与影响见 [Completion 使用审查](completion-usage-audit.md)。
已区分 kirq 事后登记、join 重试、kwork 前置准备/最终回收分配、块请求提交后
无新登记，以及 RNG 的条件等待；不能笼统认定所有使用者都不正确。

本节保留实施前的成本收益初查；最终实现见验收记录。区分三个层次：完成状态
只能有一份；登记/摘链/通知机制是否共享需要比较；等待节点的存储策略可以因
同步与多源 poll 不同。不同存储策略不必意味着两套并发状态机。

已核实：PollRegistrations 在一次逻辑等待中管理多个源，且可移动/可清除，
目前源持 Waker、owner 持 token/Weak；不能把 owner 容器中的可移动元素直接
变成侵入式节点。生产引用覆盖文件/管道/TTY、系统调用等待、task/softirqd、
workqueue 和驱动适配；搜索命中不等于这些调用点都必须修改，但回归范围较广。

Linux `fs/select.c` 的 poll_get_entry 先用内嵌条目，超出后 kmalloc 页面；
__pollwait 将条目内的 wait 节点挂到源 waitqueue。这说明“源队列不分配”与
“动态多源 poll 允许由调用方分配”可以同时成立。Linux completion 使用 swait，
普通 poll 使用 waitqueue，不能据此声称 Linux 所有等待只共用一种底层。

| 候选 | 可能收益 | 主要成本/风险 |
|---|---|---|
| Completion 另加同步登记后端，poll 原样保留 | 影响面较窄，保留现有 poll 行为较直接 | 两套登记/退出交错要维护；混合等待的令牌分发和通知不能漏掉一边 |
| 统一调用方提供节点的登记核心，同步/动态 poll 分别提供存储适配 | 复用摘链、并发通知和退出证明；同步可无分配，poll 按源数拥有存储 | 需解决可移动 owner、节点固定地址、源销毁与取消/迟到通知；避免把一次容器扩容变成每个节点一次分配 |
| 所有 poll 与 block_on 都强制无分配 | 目标表面统一 | 动态源数、通用 Future 保留 Waker 等契约大幅受影响；尚无本票需要全覆盖的证据 |

优先评估第二项的可实现性和迁移成本，而非直接选定；如果统一需要引入更复杂
的节点归还/等待同步协议，且对现有使用者收益有限，应如实比较第一项。
任何方案都不能只展示 happy path：必须列明源销毁、取消先发生、通知先摘下
节点、owner 移动/扩容、混合同步/poll 等待的退出责任与兼容成本。

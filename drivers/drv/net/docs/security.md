# drv-net — 安全与可靠性分析

## Scope

`drivers/drv/net/src/{lib,rtl8125}.rs`（约 170 行）。当前只有 probe 阶段：
纯读、无 DMA、无用户面。

## 信任模型

| 输入 | 来源 | 信任级别 |
|---|---|---|
| `segment/bus/device/function`、`vendor_id/device_id/class` | PCI 配置空间（`pci::discover` 枚举，已过滤 `0xffff`/`0x0000`） | **半可信**：来自硬件，但硬件可能是伪造/半初始化的 |
| BAR0 地址与长度 | `pci::configure_device` 分配（窗口来自 DT `ranges`） | 可信（框架保证落在本 host 解码窗口内） |
| `TxConfig` 的 xid、`MAC0/4` 站地址、`ChipCmd`/`IntrStatus`/`RxConfig` | **设备 MMIO** | **不可信**：总线可能返回全 1（未解码）、0（未上电）或残留值 |
| 寄存器偏移/位定义 | 编译期常量（对照 `r8169_main.c`） | 可信 |

关键区别：所有外部输入都**只影响判断与日志，不参与地址计算**。驱动不做
"厂商数据 → 指针/长度"的推导，因此本 crate 当前没有内存安全攻击面。

## 不可信输入的处理

| 情况 | 处理 |
|---|---|
| `TxConfig == 0xffff_ffff` | probe 失败（`RuntimeError::Io`），不进入 xid 算术——否则全 1 会被掩码成一个合法型号 |
| xid 不在 `CHIP_INFOS` | probe 失败（`Unsupported`），日志带上原始 xid 与 `TxConfig`，便于下一轮从事实出发 |
| `MAC0 == 0` 或 `0xffff_ffff` | probe 失败（`Io`）：站地址是消费者唯一会用的身份，垃圾地址比不绑定更危险 |
| `ChipCmd` 带 `CmdReset` 位 | 记 `warn`（热重启残留的复位未完成），不阻塞——当前阶段不写设备 |
| BAR0 缺失 | `dev.res().mmio(0)?` 直接传播框架错误 |

## 外部边界 / 攻击面

| 边界 | 是否触及 |
|---|---|
| 用户内存 / 用户指针 | 否 |
| MMIO / PIO | **是**——BAR0 只读访问（`read8/16/32`，volatile） |
| DMA | 否（下一阶段引入，届时需要 `kdma` 的映射与约束） |
| 固件 / ACPI 表解析 | 否 |
| `unsafe` | 无（映射与访问由 `IoMap` 封装） |
| `syscall` / ioctl 入口 | 否（未发布到 `net` 类，用户态不可见） |

## 失效模式

| 失效 | 后果 | 现状 |
|---|---|---|
| 设备未上电 / BAR 未解码 | 读回全 1 或 0 | 全 1 判失败；0 走站地址守卫判失败 |
| 芯片型号未知 | 绑定失败 | 日志给出 xid，不猜测分支 |
| 链路未训练 | 寄存器可读、收发不通 | 当前不涉及；下一阶段需要显式链路上报 |
| 复位残留 | 后续写序列可能异常 | 记 `warn`；下一阶段在复位前先等 `CmdReset` 清零 |
| probe 失败 | 设备留在域内未绑定 | 框架报 `Unclaimed`，不会静默 |

## 可靠性约束（后续阶段必须保持）

1. **先读后写**：任何写序列之前必须先确认 `CmdReset` 已清零，且型号已识别；
   8125A 与 8125B 的复位/PHY 时序不同，不能共用一条路径。
2. **DMA 缓冲必须 DMA 域名下的物理连续内存**，长度取环大小而不是包长；
   描述符所有权位是设备与 CPU 的唯一同步点（写屏障后交所有权）。
3. **不发布半成品**：`can_tx`/`can_rx` 只在环真实可服务时才返回 true。
4. **轮询兜底必须先于中断**：中断路径加进来之前，收发要在轮询模式下验证过，
   否则中断风暴会掩盖基本的环错误。
